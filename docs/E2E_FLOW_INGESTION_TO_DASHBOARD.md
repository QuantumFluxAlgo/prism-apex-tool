End-to-End Flow: Market Data Ingestion to Operator Dashboard
============================================================

1\. Market Data Ingestion and Storage
-------------------------------------

1.  **Raw Bar Ingress:** Market price bars (1-minute OHLCV) enter the system via an ingestion service. In the dev setup, an **Ingress Yahoo** microservice (apps/ingress-yahoo-dev) exposes an HTTP endpoint (POST /ingress/yahoo/v1/bar) to accept delayed Yahoo Finance data[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/ingress-yahoo-dev/src/server.ts#L46-L54). Each incoming bar payload (symbol, timestamp, open/high/low/close, volume) is validated – e.g. ensuring numeric fields and non-zero volume[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/ingress-yahoo-dev/src/server.ts#L60-L68). Bars with no volume or invalid data are skipped with an acknowledgment[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/ingress-yahoo-dev/src/server.ts#L60-L68). Valid bars trigger a **daily reset** check: if a new trading day is detected, the service resets internal risk counters (e.g. daily risk used) via resetIfNewDay[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/ingress-yahoo-dev/src/server.ts#L72-L80).
    
2.  **Bar Decoding & Caching:** The ingress service writes each validated bar to a local append-only cache. Bars are grouped by symbol and date: e.g. the service uses a helper to determine a daily bars file path and appends the JSON bar record to it[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/ingress-yahoo-dev/src/server.ts#L76-L84). This provides an intra-day log of bars (stored under .cache/bars/...) for any on-the-fly calculations. Simultaneously, the service updates running aggregates such as the **weekly VWAP** (Volume-Weighted Average Price). It loads or initializes a weekly VWAP state file (per symbol) and updates it with the new bar via stepAVWAP[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/ingress-yahoo-dev/src/server.ts#L80-L88), then computes the current VWAP value[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/ingress-yahoo-dev/src/server.ts#L86-L91). If VWAP cannot be computed (e.g. insufficient data), the bar is skipped[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/ingress-yahoo-dev/src/server.ts#L88-L91). The service also computes contextual values like **prior session high**: it reads yesterday’s cached bars and finds the previous day’s high price for the symbol[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/ingress-yahoo-dev/src/server.ts#L94-L102)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/ingress-yahoo-dev/src/server.ts#L100-L105). If that data is missing, the suggestion is skipped as well[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/ingress-yahoo-dev/src/server.ts#L96-L103). These contextual metrics (VWAP, prior high) will feed into strategy logic.
    
3.  **Initial Guardrails (Ingress):** Before generating any trade idea, the ingress service enforces basic guardrails. It maps the Yahoo continuous symbol to an internal **root symbol** (e.g. mapping ES=F → MES) for consistency[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/ingress-yahoo-dev/src/server.ts#L106-L113). It then checks a _Long-Only_ mode flag – if short trades are disallowed, any short setup is aborted (in this case the service only proceeds if LONG\_ONLY is true, defaulting to true)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/ingress-yahoo-dev/src/server.ts#L108-L111). A simple **news blackout** check is also in place (e.g. if certain times are flagged for news, skip signals)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/ingress-yahoo-dev/src/server.ts#L222-L225). With these guardrails satisfied, the service invokes a **strategy planner** for the incoming bar. For example, it calls planLongOnlyRetest from the strategy module APX-DDB-01 (Apex “delayed daily bias” strategy) to decide if the current bar warrants a trade entry[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/ingress-yahoo-dev/src/server.ts#L118-L126). This strategy uses the latest bar’s close, the weekly VWAP, and prior high to determine a potential entry, stop, and target. If no trade plan is returned (no signal under current conditions), the service responds with a no-op[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/ingress-yahoo-dev/src/server.ts#L128-L130).
    
4.  **Risk Calculation & Ticket Draft:** If the strategy yields a plan, the ingress service immediately applies **position sizing and risk caps** for this potential trade. It determines the stop distance in ticks (plan.stopTicks) and computes the per-contract risk in dollars (tickValue \* stopTicks). Using a fixed account risk budget (e.g. $200 per trade), it calculates how many contracts can be afforded (qtyRaw = floor(ACCOUNT\_RISK / riskPerContract)) and caps the quantity to a max (e.g. max 10 contracts)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/ingress-yahoo-dev/src/server.ts#L132-L140). It then computes the worst-case loss (worstCase = qty \* riskPerContract) and checks against the daily risk limit (e.g. $800 max loss per day): if taking this trade would exceed the day’s cap, it is rejected[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/ingress-yahoo-dev/src/server.ts#L134-L142)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/ingress-yahoo-dev/src/server.ts#L138-L140). Assuming it’s within limits, the service finalizes the **entry/exit prices** – rounding the planned entry to the nearest tick size, and calculating the stop-loss price and profit-target price in absolute terms[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/ingress-yahoo-dev/src/server.ts#L141-L149). It determines an expiry timestamp for the trade (e.g. end-of-day flat time from config) and composes a **Ticket** object encapsulating the trade proposal[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/ingress-yahoo-dev/src/server.ts#L151-L159)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/ingress-yahoo-dev/src/server.ts#L160-L168). This draft ticket includes: a unique id, timestamp, symbol (e.g. MESZ5 combining root and contract month), side (Buy for long), strategy (APX-DDB-01), quantity, order types (limit entry, stop-market exit, limit target), the risk-reward ratio, tick size/value, expiry time, and a notes field documenting the strategy rationale (e.g. which levels from which symbol)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/ingress-yahoo-dev/src/server.ts#L154-L162)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/ingress-yahoo-dev/src/server.ts#L166-L174). In the ticket’s metadata, the service records the source ("delayed-bias"), the guardrail parameters applied (account risk, max daily risk, etc.), and the calculated context values (VWAP, prior high, buffer ticks)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/ingress-yahoo-dev/src/server.ts#L170-L179).
    
5.  **Ticket Persistence (Ingress):** The ingress service then **persists the ticket** as an artifact for downstream processing. It writes the ticket JSON to an output directory (e.g. tickets/YYYY-MM-DD/), using a filename combining the symbol and ticket id[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/ingress-yahoo-dev/src/server.ts#L182-L190). This file-based drop (one file per ticket) serves as a handoff to the core system. After writing the file, the service updates the in-memory risk ledger – booking the risk (worstCase dollars) against the daily cap via addRisk so that subsequent signals know the remaining risk budget[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/ingress-yahoo-dev/src/server.ts#L186-L190). Finally, the ingress service responds with a confirmation { ok: true, ticket } to acknowledge that a new ticket has been generated[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/ingress-yahoo-dev/src/server.ts#L188-L191). (In a live setting, this ticket would represent a trade suggestion waiting for operator approval on the dashboard.)
    
6.  **Historical Ingestion Jobs:** In addition to live bar ingestion, the system includes batch jobs to backfill and maintain the historical price database. The **Ingest** job (apps/ingest) can be run on-demand (e.g. at deployment or for recovery) to fetch a range of historical data from Yahoo Finance. For example, the _backfill_ script fetches the last N days (default 30 days) of 1-minute bars for a list of symbols[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/ingest/src/backfill.ts#L6-L14)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/ingest/src/backfill.ts#L7-L9). It uses Yahoo’s chart API with the specified interval (1m) and aggregates results in memory, skipping null data points[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/ingest/src/backfill.ts#L90-L98). After fetching, it connects to the Postgres database and bulk upserts all bars into the bars\_1m table (with ON CONFLICT to avoid duplicates)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/ingest/src/backfill.ts#L134-L143)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/ingest/src/backfill.ts#L145-L153). Each insert covers symbol, timestamp, open, high, low, close, volume. The job then logs how many bars were written for each symbol and records an entry in an ingest\_log table (noting symbol, range, interval, and timestamp of fetch)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/ingest/src/backfill.ts#L155-L164). This ensures a historical baseline of market data in the database. There is also a scheduled **Gapfill** job that runs nightly to pick up any missing bars or to extend the data to the current time. The gapfill process computes the latest timestamp per symbol and fetches any new bars since that point (or for a fixed recent window) to keep bars\_1m continuously updated[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L200-L208). In the Docker deployment, gapfill-cron is scheduled for 02:20 UTC daily to run apps/ingest/dist/gapfill.js automatically[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L200-L208). By combining the backfill (historical) and gapfill (incremental) jobs, the system maintains a complete store of 1m bars for all traded symbols in the Postgres DB.
    

**Storage:** After these steps, the system has two main stores of market data: (a) the **bar cache/files** used by the ingress service for quick access to recent data (and by strategies like APX-DDB-01 for on-the-fly computation), and (b) the **Postgres** bars\_1m table which accumulates all historical 1-minute bars (indexed by symbol and timestamp)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/ingest/src/backfill.ts#L174-L182). The latter is used by the strategy engine for more complex analysis and by the dashboard for charting. The separation ensures the live ingress is lightweight (file-based) while the DB serves as the source of truth for historical queries.

2\. Strategy Engine & Signal Generation
---------------------------------------

1.  **Engine Trigger:** The core **Strategy Engine** runs either on a schedule (e.g. at session start or specific times) or on demand to analyze accumulated market data and produce trade signals. The system provides an **EngineRun job** (apps/api/src/jobs/engineRunJob.ts) which acts as an entry point to execute a strategy for a given symbol and session date. For example, the function runEngineSessionJob accepts parameters {strategy, symbol, sessionDate, ...} and orchestrates a full strategy run. In a live scenario, this might be triggered at the beginning of a trading session or when new data warrants re-evaluating a strategy. (Multiple strategies or symbols can be run in parallel via separate job invocations, or sequentially via an **EngineReplay** job for backtesting multiple sessions.) The engine job first parses the risk configuration (e.g. max dollars risk per trade) from its inputs or environment and prepares a EnginePreviewRequest DTO for the strategy.
    
2.  **Loading Data & Strategy Selection:** The engine then loads the necessary market data and executes the specified strategy logic. Internally, it calls runEnginePreview(request) in the Strategy Engine service. This function (defined in apps/api/src/services/strategy-engine/index.ts) retrieves all 1-minute bars for the given symbol and session date from the bars\_1m table (ensuring it has the full session’s data) and then selects the appropriate strategy algorithm. The system supports multiple strategies; for example:
    
    *   **Opening-Session Breakout (OSB)** – identified by key "osb".
        
    *   **VWAP First Touch (VWAP\_FT)** – key "vwapft".
        
    *   **Open-Range Retest (ORR)** – identified internally as "orr" (which corresponds to the APX-DDB-01 strategy in tickets).The engine maps the strategy key from the request to the implemented function. It loads the tuned strategy parameters from configuration (potentially using a “promoted” version of the strategy config) and then invokes the strategy function with the historical bars and those parameters. For example, if strategy="orr", it ensures the config payload matches the ORR strategy and calls runOrrStrategy(bars, params) to compute signals. Each strategy function processes the bar series and returns a set of **raw signals** – potential trade entries with attributes like direction (long/short), entry price, stop price, target price, and a timestamp for when the signal occurred.
        
3.  **Signal Filtering – Safety Envelope:** Once raw signals are generated, the engine applies a **Safety Envelope** filter. This is a risk mitigation step (often based on volatility or price range) that can drop any signals deemed too risky or outside allowed bounds. The engine calls applySafetyEnvelope(signals, bars, context) which returns a subset of approved signals and a count of how many were rejected as outliers. For instance, the safety envelope might ensure that entries aren’t too far from a moving average or that the price hasn’t moved beyond a threshold; any signal failing these conditions is filtered out. The number of signals dropped by this envelope is recorded in the engine’s metadata (as safetyEnvelopeDropped).
    
4.  **Signal Filtering – Hard Stop Gating:** Next, the engine enforces a **hard stop risk check** at the signal level. This is similar in spirit to what the ingress service did, but applied uniformly to all strategies. If a maxRiskDollarsPerTrade is defined (either via ENGINE\_MAX\_RISK\_DOLLARS\_PER\_TRADE env or job param), the engine will eliminate signals that cannot possibly fit into that per-trade risk budget. It uses applyHardStopToSignals to evaluate each signal’s stop distance in dollars against the limit. Essentially, if a signal’s stop loss is so wide (or the price so volatile) that even a single contract would exceed the dollar risk cap, that signal is dropped immediately. Signals that pass this check are considered **approved signals** and carry forward. The engine logs whether the hard-stop gating was enabled and the value of the cap in its run notes (e.g. “hardStop=enabled(max=$X)”).
    
5.  **Enriching Signals with Meta:** For the signals that remain, the engine adds some useful metadata. For example, it calculates the number of ticks from entry to stop (ticksToStop) and the per-contract risk in dollars, attaching these to each signal object. This enrichment doesn’t change the decision, but it prepares the data for downstream ticket construction and for operator visibility (so that one can see how far the stop is, etc.). At this point, the engine has a final list of **EngineSignal** objects ready to be turned into concrete trade tickets.
    
6.  **Engine Output (Preview):** The runEnginePreview function then assembles an **EnginePreviewResponse**. It includes the strategy, symbol, session date, and the list of **signals** (each enriched as above). It also compiles metadata about the run: for example, the engine version, the risk engine version, the strategy config version used, how many bars were processed, the session start/end timestamps, and any special notes. Notably, it records the count of signals dropped by the safety envelope and possibly other gating info (so the operator or developer can see if signals were filtered out). This preview result is then returned up to the EngineRunJob.
    
7.  **Engine Job Summary:** The runEngineSessionJob (EngineRun job) receives the preview and extracts the signals and meta. If **no signals** came out of the strategy (common if no trade setup occurred), it will log a summary indicating zero signals and skip ticket generation. In such a case, it still records the engine version and safetyEnvelopeDropped count, and sends an alert/event that “No signals returned; skipping tickets pipeline”. If there are signals, the EngineRun job proceeds to the ticket pipeline (next section). Either way, it logs a JSON summary of the run (including how many signals, tickets, rejections, etc.) for governance and debugging. The system may also raise alerts if certain conditions occur – for example, if any signals were rejected due to hard stop (logged as a “hard\_stop\_drops” alert with the count of rejected signals). This ensures that risk filters dropping trades get visibility.
    

_(At this stage, the strategy engine has effectively transformed raw market data into potential trade_ _**signals**__, with initial risk constraints applied. Next, those signals are fed through the_ _**Ticketization**_ _process to produce final trade tickets.)_

3\. Ticket Generation, Guardrails & Finalization
------------------------------------------------

1.  After processing all signals, the function returns a **TicketBuildResult** with two lists: tickets (approved MinimalTickets) and rejected (with each original signal plus rejection reason). This conversion ensures that each strategy signal either yields a properly sized trade ticket or is documented as filtered out due to risk.
    
    *   It determines the candidate entry price and stop price from the signal (using the signal’s specified entry or current price, and its stop level). If either price is invalid or missing, that signal is immediately marked as rejected (“Missing or invalid entry/stop”).
        
    *   For a valid signal, the builder performs a **Hard-Stop Evaluation** to decide contract size. This uses the evaluateHardStop function which takes the symbol’s price difference between entry and stop and the configured max risk per trade. If a specific contract count was requested (not usually the case for strategy signals), it would validate that against the risk; otherwise, it computes the maximum contracts such that riskDollars <= maxRiskDollarsPerTrade. It effectively does: contracts = floor(maxRisk / (ticks\_to\_stop \* dollars\_per\_tick)). If even 1 contract would breach the risk limit, the decision comes back **rejected** (“Unable to size even a single contract within per-trade risk limit” or similar). If a contract amount is feasible, it returns an approved decision with the number of contracts and the calculated risk in dollars.
        
    *   If the decision is **approved**, the builder creates a **MinimalTicket** object. It generates an id (concatenating strategy, symbol, and signal timestamp to ensure uniqueness) and populates the ticket fields: symbol, strategy, **direction** (LONG/SHORT from the signal), the decided contracts count, the entry price, stop price, and target price (if the strategy provided one). It also stores the exact risk in dollars (per trade) and, if available, the expected reward and R:R multiple (reward/risk) for the trade. The ticket carries over some engine context: the time the signal was generated (engineTimestamp) and references to the engine and strategy versions for traceability. If the signal had any specific reason code (e.g. describing its scenario), that can be attached as well. All approved tickets are collected in a list.
        
    *   If the decision for a signal is **not approved** (e.g. risk too high), the builder logs it as a **rejected signal** along with the HardStopDecision reason. The signal and reason get added to a rejected list for record-keeping.
        
2.  **Persistence of Engine Tickets:** The Engine Tickets Pipeline then calls persistEngineTickets to save these results to the database. In apps/api/src/services/tickets/engineTicketsStore.ts, each ticket is mapped into a database row and inserted into the engine\_tickets table. Key fields like symbol, strategy, direction, contract count, prices, and risk are stored, along with the session date and a status ('approved' or 'rejected'). Rejected signals are stored with contracts=0 and their rejection reason (e.g. “Requested contracts exceed per-trade risk limit”) in a column. The insert uses a transaction to write all tickets and rejections in one go. This **engine\_tickets** table is mainly for analysis and auditing – it holds the raw outputs of the strategy engine before final operator-facing guardrails. It’s useful for reviewing what the strategy _would_ have suggested and which got filtered out by hard risk limits.
    
3.   When a **Suggestion** event arrives (suggestion = potential ticket with symbol, side, prices, etc.), the Ticketizer’s onSuggestion handler is invoked asynchronously. It first records a heartbeat (for monitoring) and timestamps the suggestion. Then it checks **daily risk lockout**: if the operator has hit the daily loss limit (tracked elsewhere), new tickets might be globally blocked. It calls shouldBlockNewTicketsForDay(tradingDay) to see if a lockout is in effect. If yes, Ticketizer will **reject** the suggestion outright – it logs a warning, creates a system alert (“Daily risk lockout active: new tickets blocked for the day”), and records an audit entry. In this case, no ticket will be issued. (This mechanism ties into an operator risk management module, ensuring the system doesn’t feed new trades when the day’s allowed drawdown is met.) If not locked out, Ticketizer proceeds to apply all guardrail rules via applyGuardWithSizing (from the @prism-apex/rules-apex package). It prepares a context with the account phase (evaluation or funded), the max contracts allowed for the account, whether the trailing drawdown buffer is cleared, recent ticket sizes, and the “flatBy” end-of-day cutoff time. Before sizing, Ticketizer has one more time-based rule: it checks if the suggestion’s timestamp is within ~5 minutes of the session close (the **EOD flat window**). If so, it will forcefully suppress the trade – returning a Ticket marked accepted: false with reason "preclose-suppression" (meaning it’s too late in the day to open new positions). This EOD guard ensures compliance with rules that all positions should be flat by a certain time. Assuming we are not in the flat window, applyGuardWithSizing evaluates all rules on the suggestion:Ticketizer then constructs the final Ticket to record the outcome. If accepted, it flags it and notes which guardrails were applied (via a meta.guardrails array, e.g. "phase:funded", "buffer" cleared or not, "anti-windfall" if any were triggered). It also may add a consistencyNotes field if relevant (for example, marking a ticket as metrics-only if we’re in a consistency evaluation period). If rejected, it similarly creates a ticket with accepted=false and fills in the reasons array (e.g. \["min-rr-not-met"\] or \["daily-lockout"\]). Notably, even rejected suggestions are turned into Ticket objects here – this way they can be logged and seen by the operator (often with a strike-through or warning in the UI) for transparency.
    
    *   **Stop on correct side & required:** ensures the suggested stop loss is placed logically (e.g. below entry for a buy) and exists.
        
    *   **Risk/Reward clamp:** enforces a minimum R:R (e.g. reject trades with RR < 2.0 or unrealistically high RR > max).
        
    *   **Consistency rules:** e.g. if the operator hasn’t demonstrated consistency, new tickets might be half-sized until a “buffer” (profit) is cleared.
        
    *   **Half-size until buffer cleared:** if the telemetry indicates the account is still in a drawdown buffer, the rule may cut the size in half (this is reflected as a guardrail tag like "half-size-until-buffer").
        
    *   **Anti-windfall rule:** prevents too large a size increase after a big win.These rules are implemented in rules-apex and return a result with either an accepted ticket (with possibly adjusted qty and added notes) or rejection reasons. For example, if all rules pass, Ticketizer gets back an accepted **Ticket** object (similar shape to the earlier Ticket, but now including guardrail metadata and any size adjustments). If a rule fails (say R:R is below minimum), the result will indicate not accepted and include the reason (which Ticketizer will attach).
        
4.  **Final Ticket Logging:** Once Ticketizer produces the final **Ticket**, it saves it to the central Ticket Store and notifies other components. It calls saveTicket(ticket) which appends the ticket (along with a unique hash) to a JSON Lines file (tickets.jsonl) on disk and keeps an in-memory index[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/api/src/store/tickets.ts#L48-L56)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/api/src/store/tickets.ts#L54-L62). The store ensures each ticket is stored exactly once by checking a hash set (to avoid duplicates)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/api/src/store/tickets.ts#L48-L56). The ticket record includes everything needed for the UI: symbol, side, entry/stop/target, quantity, accountId, timestamp, meta (strategy name, RR, guardrails applied, etc.), whether it was accepted, and any rejection reasons. Storing to this append-only log means the day’s tickets can be retrieved quickly and also persisted across restarts (in local deployments). After saving, Ticketizer publishes a 'ticket' event on the bus[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/ingress-yahoo-dev/src/server.ts#L182-L190), which could be used to live-update any WebSocket or to trigger downstream logging. It also updates internal counters for monitoring (e.g. incrementing how many tickets of each strategy were accepted or rejected, and recording the last accepted timestamp) to be able to display stats on the dashboard or logs.
    
5.  **Disk Sync (for Ingress):** If tickets were generated by external services (like the ingress-yahoo writing files), the system can import them via a **Tickets Disk Sync** job. The ticketsDiskSync routine scans the tickets/ directory for any JSON ticket files not yet processed, reads them, validates against the Ticket schema, and then calls the same saveTicket() to record them. In Docker dev setups, a sidecar (tickets-sync) can be running to continuously sync these files. This way, even tickets created by the Yahoo ingress service (which bypass Ticketizer’s live guardrails) are eventually pulled into the main ticket store and shown on the dashboard. Each synced file is marked as processed (to avoid duplicates on restart). In practice, for the **current live system**, the primary path for tickets is through the Ticketizer (for strategies like OSB and VWAP\_FT), whereas the APX-DDB-01 (ORR) strategy tickets may arrive via the file system and get synced. The goal is that **all ticket data flows into a unified store** that the operator dashboard reads.

These jobs work in concert to ensure the system’s data and risk state are up-to-date. For example, **session metrics** like daily P/L and drawdown are computed on the fly by the Telemetry client (summing fills and tracking balance changes). The system also logs a **risk audit** for certain events (like if a daily loss limit triggers a lockout, or if an operator override happens) – these are stored via recordRiskLockout and similar calls in an audit log table for later review.

At the end of each trading session, the combination of the tickets generated and the telemetry data allows computing metrics such as:

*   **Signal adherence** – how many suggested tickets were actually placed by the operator (could be inferred by comparing tickets vs. fills in telemetry).
    
*   **Daily Profit/Loss** – via telemetry’s fills and account balance.
    
*   **Win/Loss ratios, average RR** – from ticket outcomes (if linked with fill results, once the day is done).
    
*   **Consistency Score** – an internal metric (from the consistency module) that measures if the operator is following the system’s signals or deviating. The system can flag inconsistencies (e.g. missing a winning trade or manual trades outside of suggestions) for review.
    

Currently, these session metrics are primarily internal or in development – e.g. the @prism-apex/consistency and @prism-apex/analytics packages would handle computing such stats. They influence downstream processing by adjusting guardrails: for instance, if consistency is not yet proven, the system might enforce smaller size (as noted by the guardrail "half-size-until-buffer" which stays until a profit buffer is achieved). In summary, the jobs infrastructure ensures that by the time a session concludes, all data (market, tickets, execution) is recorded, and any rule-based limits (daily loss, etc.) are enforced in the subsequent sessions.

5\. Data Flow to Operator Dashboard
-----------------------------------

1.  **Backend API Services:** All the processed data – from market bars to tickets and telemetry – is exposed through the **API layer** (apps/api). The API is a Fastify server that provides REST endpoints used by the operator’s dashboard. Key routes include:
    
    *   GET /metrics – returns a summary of system metrics (e.g. bar counts, total tickets, last ingest time, DB connectivity)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/api/src/routes/metrics.ts#L60-L68)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/api/src/routes/metrics.ts#L70-L78).
        
    *   GET /metrics/bars?symbol=X&granularity=Y – returns recent price bars for symbol X at resolution Y (e.g. 1m or aggregated 5m) for charting[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/api/src/routes/metrics.ts#L123-L131)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/api/src/routes/metrics.ts#L133-L141).
        
    *   GET /tickets – retrieves the list of tickets (with filtering options by date, strategy, status, etc.)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/api/src/routes/tickets.ts#L86-L94)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/api/src/routes/tickets.ts#L100-L109).
        
    *   GET /telemetry/account?accountId=... – gets the latest account status (balance, drawdown buffer, etc.) for the given account[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/api/src/routes/telemetry.ts#L10-L16).
        
    *   GET /telemetry/positions?accountId=... – lists current open positions (if any) from telemetry[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/api/src/routes/telemetry.ts#L6-L14).
        
    *   GET /telemetry/fills?accountId=...&date=YYYY-MM-DD – gets executed trades for that account/date[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/api/src/routes/telemetry.ts#L18-L26).Many of these routes simply query in-memory stores or the database and return JSON. For example, the **Tickets API** will, in production mode, connect to Postgres and run a query to get the latest tickets from the tickets table (joining with other info)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/api/src/routes/tickets.ts#L88-L97)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/api/src/routes/tickets.ts#L100-L109). It uses filters for symbol, strategy, date range, etc., and supports pagination (limit/offset). In a no-DB scenario (or test mode), it falls back to the in-memory JSONL store: using listTickets(date) to page through the tickets loaded in the file[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/api/src/routes/tickets.ts#L117-L125)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/api/src/routes/tickets.ts#L124-L132). This dual-mode design ensures the dashboard can operate even if it’s just reading the local file (useful in eval environments).
        
2.  **Frontend (Dashboard) Components:** The operator interface is a React application (apps/dashboard) that interacts with these APIs. Upon loading, the dashboard fetches data and continually updates it. For example:
    
    *   The **Market Data** page of the dashboard calls /api/metrics to get the overall system status and stores summary stats (like how many bars in DB for each symbol, how many tickets today, last ingestion timestamp)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/dashboard/src/pages/MarketData.tsx#L105-L113). It then displays these, giving the operator a quick health check (e.g. “DB connected: true, Bars loaded for ES=F: 10,000 bars from date X to Y, Tickets today: 2, Last data fetch: 2025-12-12T14:00Z”).
        
    *   The Market Data page also lets the user select a symbol and time resolution to view a price chart. When a symbol or granularity is selected, the dashboard calls /api/metrics/bars?symbol=SYM&granularity=1m (for example) to retrieve the recent candles[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/dashboard/src/pages/MarketData.tsx#L120-L128)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/dashboard/src/pages/MarketData.tsx#L124-L132). The API responds with an array of bar points ({ts, open, high, low, close, volume}), which the frontend uses to plot a candlestick chart. This update happens on an interval (the dashboard by default refreshes the chart data every 60 seconds)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/dashboard/src/pages/MarketData.tsx#L140-L148), so the operator can see near-real-time price movement. The chart also overlays indicators like VWAP or ATR – these are computed client-side from the bar data (the UI code toggles VWAP/ATR lines based on user input).
        
    *   There is likely an **Active Tickets or Signals** view which calls the /api/tickets endpoint. The dashboard might fetch tickets for the current day (e.g. GET /api/tickets?date=2025-12-12) to get all tickets generated today. The data returned includes each ticket’s fields exactly as saved. The React component (e.g. TicketsTable) then renders a table: each row showing Time, Symbol, Side, Entry, Stop, Target, RR, Qty, Strategy, and Accepted status[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/dashboard/src/components/TicketsTable.tsx#L64-L73)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/dashboard/src/components/TicketsTable.tsx#L74-L81). In the UI, accepted tickets might be highlighted normally, while rejected ones (accepted=false) could be shown with an ❌ or different style (the table includes a checkmark or cross in the “Accepted” column with a tooltip of reasons if not accepted[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/dashboard/src/components/TicketsTable.tsx#L70-L78)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/dashboard/src/components/TicketsTable.tsx#L74-L81)).
        
    *   The **TicketsTable** also provides quick-action buttons. For each ticket, the dashboard offers one-click copy for the entry price, stop, target, quantity, or a full “order block” text[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/dashboard/src/components/TicketsTable.tsx#L76-L84). The “Order Block” is a concatenated string of the ticket parameters (symbol, side, qty @ entry, SL, TP, RR)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/dashboard/src/components/TicketsTable.tsx#L24-L32)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/dashboard/src/components/TicketsTable.tsx#L26-L34) that matches the format the operator needs to input into Tradovate. By clicking these, the operator can swiftly transfer the suggested trade into the trading platform. This is an important part of the “operator-in-the-loop” design: Prism-Apex generates the **ticket**, and the human acts on it by manually placing the trade in Tradovate (since **no auto-order is ever sent** by Prism-Apex[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/TESTING.md#L35-L43)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/TESTING.md#L37-L45)).
        
3.  **Operator Actions & Feedback:** The dashboard does not directly send trade commands (per design, orders are manual), but it does reflect the outcomes via telemetry. When the operator places a trade in Tradovate (using the info from the ticket), the **Telemetry job** will pick up the new position or fill. For instance, if the operator went long 2 MES contracts at the suggested price, the telemetry snapshot will include that position. The dashboard could have a section (or a separate “Positions” page) showing current positions via /telemetry/positions and recent fills via /telemetry/fills. These routes simply read from the telemetryStore updated by the polling job. The telemetry data also includes whether the “Trailing Drawdown buffer” is cleared (a boolean). The Ticketizer used this to decide if full size is allowed; the dashboard can also display it (maybe as part of account status). For example, an account card might say “Trailing drawdown buffer: **cleared**” or not, to explain if half-sizing is in effect. All this info (account balance, P/L, buffer, positions) comes from periodic snapshots published by the telemetry client[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/api/src/jobs/telemetry.ts#L20-L28)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/api/src/jobs/telemetry.ts#L22-L26).
    
4.  **Operator Risk & Alerts:** If any risk thresholds are hit during the session, the system surfaces that on the dashboard as well. For instance, if a **daily loss limit** is exceeded, the shouldBlockNewTicketsForDay will start returning true. The Ticketizer, as noted, creates a **System Alert** in such cases. The API has an endpoint (or could easily have) for system alerts, or it may embed active alerts in the /opsStatus or /status route. The dashboard can show a prominent warning (e.g. “Daily loss limit reached – system will not issue new tickets.”). Similarly, if Ticketizer ever rejects a ticket due to a guardrail, the reason is attached to the ticket and visible as a tooltip in the UI[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/dashboard/src/components/TicketsTable.tsx#L70-L78). This transparency helps the operator understand why a suggestion was not actionable (for example, “✗ (preclose-suppression)” if it came after the cutoff).

All these pieces ensure that data flows from **ingestion → database → strategy engine → guardrails → ticket store → API → frontend** in a coherent pipeline. The current live system prioritizes producing **tickets only** (never automated orders)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/TESTING.md#L35-L43), enforcing **risk rules** at multiple stages (ingress, engine, and final issuance), and providing the operator with clear information and tools (copyable trade details, alerts, countdowns) to execute trades confidently and within the prop firm’s rules. The architecture separates concerns into modules but links them via well-defined DTOs and events – for example, EngineSignal -> MinimalTicket -> Ticket, or the suggestion bus events – to maintain a robust and traceable decision trail from raw market data all the way to the operator’s screen.
