MONOREPO\_ARCHITECTURE.md
=========================

1\. Executive Summary
---------------------

**Prism-Apex Tool** is an operator-assisted trading system designed for **Apex Trader Funding** accounts on Tradovate. It serves as the “brain” that generates trade **tickets** (entry/exit suggestions with built-in risk controls) while a human operator acts as the “hands” executing trades manually[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/README.md#L190-L194). This monorepo’s primary mission is to **automate signal generation and risk guardrails** without ever placing real orders automatically[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/README.md#L188-L194). All automated processes stop at ticket creation – a strict program rule to remain compliant with Apex funding requirements[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/README.md#L435-L439). The monorepo integrates data ingestion, strategy evaluation, risk management, and operator dashboards to solve the business problem of **systematic trading within Apex’s rules**. By enforcing Apex’s limits (e.g. stop-loss requirements, profit targets, drawdown limits) in code, it helps prevent rule violations and improve consistency[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/README.md#L231-L238). This ensures traders can focus on execution while the system handles calculations, record-keeping, and compliance checks.

This repository is intended for use by **internal engineers and architects** who develop and maintain the trading logic, infrastructure, and UI, as well as by **risk/governance personnel** who ensure the code adheres to non-negotiable constraints (e.g. “tickets-only” policy). Senior engineers onboarding to the project will use this document to quickly understand the overall architecture, major components, and design constraints. The focus is on accurately capturing the “ground truth” of the codebase – every claim here is backed by repository evidence or explicitly marked _UNVERIFIED_ if uncertain. This document also serves as a basis for architectural governance, helping the team make consistent design decisions and **safely evolve the system without regressing on critical safety rules** (like not accidentally introducing auto-trading). In summary, Prism-Apex Tool is a **Docker-first**, TypeScript-centric monorepo that generates trade tickets under strict guardrails[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/README.md#L188-L196)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/README.md#L231-L238), and this document codifies its architecture for ongoing high-level guidance.

2\. Repository Topology
-----------------------

**Monorepo Scope:** The repository is structured as a **single workspace** containing multiple applications and packages. It follows a clear separation of concerns between entry-point services, shared libraries, and configuration/infra code. Below is a top-level directory map with each major area’s purpose and ownership:

*   **apps/api/** – Entry-point **API server**, written in Node/TypeScript. Provides REST (and possibly WebSocket) endpoints for system telemetry, health checks, readiness, and serving trade tickets (JSON/CSV downloads) to operators[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/README.md#L399-L402). This is the backend “brain” exposing the signals and data in a controlled, read-only manner. Owned by backend engineers.
    
*   **apps/dashboard/** (and apps/dashboard-lite/) – **Operator dashboard** UIs, built with Vite/React for web. The Dashboard provides a user interface for operators to review tickets, monitor account status, and see strategy telemetry[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/README.md#L399-L402). The “full” dashboard is served via a production web server (Nginx) for deployment, while “dashboard-lite” is a pared-down or dev version (used for faster local iteration) – _UNVERIFIED exact differences_. These are owned by front-end engineers and interact with the API. Epic 1 consolidated all REST calls through `apps/dashboard/src/lib/api.ts` and added `/api/*` contract telemetry (`lib/contractTelemetry.ts`) so every page now emits page-load markers and route-specific error breadcrumbs when the API fails.
    
*   **apps/ingress-yahoo-dev/** – **Market data ingress service** for Yahoo Finance (15-minute delayed data). This Node service runs in Docker (port 8080) to fetch or stream market data and feed it into the system[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L109-L117). In local and prod compose profiles, ingress-yahoo is responsible for populating the database with price bars via Yahoo’s API (simulating a live feed). Owned by data ingestion/infra engineers.
    
*   **apps/ingest/** – **Batch ingest job** (Node/TS). This is a one-shot process for backfilling historical market data into the Postgres database[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L137-L145). It fetches a specified range of historical price candles (by default ~30 days of 1-minute data for configured symbols) from Yahoo and stores them. It’s run on demand (e.g. make seed) or as part of initial environment bring-up.
    
*   **apps/tickets/** – **Ticket generation job** (Node/TS). This produces strategy output tickets over a historical window or continuously. For example, it runs the **Opening-Session Breakout** and/or other strategies on recent data to append new trade tickets to the log[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L174-L182)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L223-L228). In Docker Compose, a tickets-once job backfills recent days’ tickets, and a tickets-cron service runs the ticket generator continuously (every 60 seconds) for live operation[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L219-L228). This code ensures strategies are executed on schedule and tickets are written, without any human input.
    
*   **packages/** – **Shared core libraries** used by the above apps[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/README.md#L399-L406). These are plain TypeScript libraries (no standalone processes) providing domain logic: technical indicators, strategy algorithms, risk rule implementations, account-state modeling, etc. Each sub-folder in packages is a versioned package in the PNPM workspace (often prefixed @prism-apex/\*). They encapsulate business logic and utilities so that multiple apps can reuse them consistently. This area is jointly owned by all engineers (with specific packages often owned by subject-matter experts, e.g. a quant owning strategies/). Key packages are described in the next section.
    
*   **configs/ and config/** – **Configuration files and templates**[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/README.md#L402-L405). The configs/ directory contains JSON configs for strategies, guardrails, etc. (for example, per-strategy parameters and schedule toggles) and possibly environment-specific settings. The config/ directory (singular) holds environment templates and higher-level config (e.g. .env.template or composite config files like contracts-spec.json). Together, these define tunable parameters (e.g. which strategies are active, risk limits) outside of code. Changes here should be reviewed carefully as they directly affect runtime behavior.
    
*   **tickets/** – **Ticket logs** (output data). This folder stores the append-only JSONL files that record every generated trade ticket[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/README.md#L403-L406). Each trading day has its own log file. These files are **sacrosanct records** of what the system signaled; they are never to be retroactively edited or deleted, only archived if needed (per compliance)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/README.md#L520-L523). Both the API and Dashboard read from here (directly or via the API) to display historical and current trade recommendations.
    
*   **scripts/** – **Operational scripts and tooling**[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/README.md#L402-L405). Bash and Node scripts for development and maintenance live here. Examples: local-up.sh and local-down.sh to start/stop the dev stack, cleanup\_repo.sh for removing generated clutter, scan\_repo.sh to find forbidden patterns, etc. These are primarily for developers’ productivity and enforcing repo standards (like the _no-order-placement_ guard). There is also a bin/ directory for some specialized scripts (e.g. bin/backfill.sh to trigger backfill workflows via GitHub CLI[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/bin/backfill.sh#L2-L10)).
    
*   **docs/** – **Documentation and runbooks**[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/README.md#L403-L407). This includes architecture notes, specifications, operational runbooks, glossaries, and compliance documentation. Many .md files here (e.g. AGENTS.md, TECH-SPEC.md, OPERATIONS.md) outline how the system works or how to perform certain tasks. These docs are considered part of the codebase truth (some are auto-generated from content in the repo) and should be kept in sync with code changes. New engineers are expected to read these for deeper context.
    
*   **Infrastructure & Config files:** In the repository root, you’ll find **Docker compose files** (docker-compose.yml plus profile-specific overrides) and Dockerfiles, which define how the services run in containers[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/README.md#L405-L408). There are also CI config files under .github/, an .eslintrc.cjs for linter settings, a Makefile for common compose commands, and environment example files (e.g. .env.template, .env.docker.example). These ensure a consistent runtime environment (ports, credentials, build settings) and are maintained by DevOps-minded contributors.
    

**Entrypoints vs Shared vs Leaf:** The **entrypoint services** are under apps/ (API, dashboards, ingress, jobs) – these are the only modules that produce runtime processes or deliver UI/HTTP interfaces. They all depend on the shared packages for their core logic. The **shared infrastructure code** (in packages/, plus configs/, scripts/, etc.) provides the reusable logic and config management that underpin these apps. Many packages are self-contained and do not depend on each other (e.g. calculation libraries), serving as **leaf packages** in the dependency graph. This means the dependency direction is mostly one-way: apps → packages, and sometimes one package → another, but never apps → apps. We explicitly avoid cyclical or cross-boundary dependencies to keep the architecture modular. For example, the front-end never directly imports back-end code, and strategy code is isolated from API server code (they interact via well-defined interfaces such as function calls or data files, not tight coupling). Each package’s position as core vs. leaf is detailed below, along with any known ownership or stability notes.

### Applications / Services (Entrypoints)

*   **API Server** (apps/api, **TypeScript Node 20**):
    
    *   **Responsibility:** Implements the back-end HTTP API for the system. It hosts health and readiness endpoints, serves the latest tickets data, and may expose other telemetry or reference data for the UI[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/README.md#L399-L402). It also orchestrates strategy execution indirectly: it contains job modules that can trigger strategy runs or integrate results (e.g. src/jobs/strategies.ts, src/jobs/ticketizer.ts). The API does **not** initiate trades; it only provides data and status.
        
    *   **Public Interfaces:** A Fastify HTTP server listening on port **3000** (in Docker). Key GET endpoints include /health, /ready, /openapi.json, /version for basic status[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/TECH-SPEC.md#L37-L45), and endpoints to fetch tickets (GET /tickets?date=YYYY-MM-DD for JSON, /export/tickets?date=YYYY-MM-DD for CSV)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/TECH-SPEC.md#L107-L115). It likely also serves symbol metadata (/api/symbols/v2 for contract specs[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/README.md#L422-L425)) and possibly streaming or WebSocket endpoints for live updates (not explicitly confirmed). All API endpoints are read-only or diagnostic – there are no authenticated trading or order submission endpoints (by design, no order placement)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/README.md#L435-L439).
        
    *   **Upstream Dependencies:** Depends on **PostgreSQL** (for reading bar data and possibly account state) and the local **tickets files** (for serving tickets). Within the code, it imports many internal packages: strategies, rules, ticketizer, consistency, etc., to perform its functions. It also uses Fastify and likely ORMs or DB drivers (e.g. pg via a data access layer) for database access. Environment variables like DATABASE\_URL and feature flags (e.g. TICKETS\_ONLY=true, which is always true in this project) are provided to configure its behavior[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L51-L59).
        
    *   **Downstream Dependents:** The **Dashboard** (and any other client) calls this API to get data. The tickets-cron service depends on API (compose sets depends\_on: api for tickets-cron)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L229-L235) – this is mainly to ensure the API is up when the cron starts (and perhaps to reuse the API container’s image for running jobs). No other services call into the API except through HTTP. Engineers depend on the API as the integration point for new logic (e.g. adding a new endpoint for a report).
        
    *   **Stability:** **Core stable.** This is a central piece of the system – changes here affect the whole platform. Its interface (endpoints) should remain backwards-compatible whenever possible, especially since the UI and possibly external operator tools depend on it. The API code itself may evolve as new data or compliance checks are added, but fundamental behaviors (health checks, tickets retrieval) are well-established. Expect medium churn during active development of new features, but any change that could affect ticket integrity or health semantics is high-risk and should be reviewed. The absolute rule that it must never initiate orders is permanent[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/TESTING.md#L180-L184) (breaking that would violate project invariants).
        
*   **Dashboard (Full)** (apps/dashboard, **TypeScript + React**):
    
    *   **Responsibility:** A **web front-end** for operators to review signals and system status. It displays the ticket list (with details like entry/stop/target, R:R ratio, etc.), and various status panels such as guardrail alerts, countdown to end-of-day flat time, account balance or drawdown, etc. Its goal is to give the operator all information needed to confidently and safely execute the suggested trades[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/GLOSSARY.md#L130-L139)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/GLOSSARY.md#L160-L169). The “full” dashboard is optimized for production use, likely including all visualizations and served via an Nginx web server for efficiency.
        
    *   **Public Interfaces:** A browser UI (HTML/JS/CSS). In production, it’s served on port **5180** (mapped to container’s port 80) via an Nginx container[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L73-L81)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L83-L90), accessible over HTTP. The dashboard itself calls the API (proxy or direct) to get JSON data. It does not expose an API of its own except the static content. In development, running pnpm dev on this app starts a Vite dev server on port 5173 (or 5178/5179 in some setups)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/AGENTS.md#L148-L156)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/TESTING.md#L154-L162). It also depends on shared utility packages for consistent logic – for example, it uses @prism-apex/shared/contracts to load contract specs for tick sizes and PnL calculations[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/README.md#L414-L421). It may also use other shared packages (e.g. shared for formatting or types, metrics for interpreting data). Configuration is via environment variables for build: e.g. VITE\_API\_BASE to know the API URL[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/README.md#L422-L425). No direct database or file access (all data comes from the API or embedded config like contracts-spec.json).
        
    *   **Downstream Dependents:** None (it’s an end-user interface). The only “clients” are the human operators using a web browser. However, other tools could be built to consume the same API if needed. For governance, any structural changes here must be coordinated with API changes (e.g. if API payload changes, update UI accordingly).
        
    *   **Stability:** **Moderately stable UI.** The dashboard is expected to evolve with user feedback – adding new views, metrics, or supporting new strategies – but its core purpose (displaying tickets and alerts) remains constant. Changes to this app are lower-risk in terms of business rules (a UI bug won’t violate trading rules, but could confuse operators), yet high-risk in terms of user experience (a poor UI can lead to misuse). It should remain backward-compatible with API changes (or be updated in lockstep). Since operators rely on it, avoid drastic redesigns without a rollout plan. Expect iterative improvements and occasional larger updates when strategies or requirements expand.

The service then writes this data to the Postgres database (into tables like bars\_1m) and possibly caches some locally. Essentially, it ingests live (delayed-live) market data so that strategies can operate without a direct broker feed[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/TECH-SPEC.md#L48-L56). Tests or simulations (like apps/ingress-yahoo-dev/test/ingress.test.ts) presumably cover typical flows. *   **Tickets Generator (ORR job)** (apps/tickets, **TypeScript Node**):
    
    *   **Responsibility:** The automated **strategy runner** that produces trade tickets. It runs the configured strategies on recent market data and appends any qualifying trade “ideas” to the tickets log. The primary strategy currently implemented here is the **Opening-Session Breakout (OSB)**, referred in code as “ORR” (possibly _Opening Range Rotation_ or similar). The job uses the latest data (from DB) and strategy logic (from packages/strategies and related packages) to decide if a ticket should be created for a given interval. In backfill mode, it can generate tickets for past days (to simulate what would have happened). In live mode, it runs continuously (every minute) to generate real-time suggestions[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L223-L228). This separation allows the core API to remain stateless, while this job handles timing and stateful iteration.
        
    *   **Public Interfaces:** Also a CLI/batch style like ingest. It defines a script "backfill:orr": "node dist/backfill-orr.js" to run a backfill of recent tickets[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/apps/tickets/package.json#L6-L14). Under Docker, tickets-once runs that script for the last N days (default 30 days)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L168-L176), and tickets-cron launches an infinite loop calling the same script every 60 seconds[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L219-L228). The job prints to console (compose logs) when it runs and if it generates tickets (for debugging). No direct external interface – the output is the JSONL files in tickets/ and new entries in the tickets DB table (if one exists).
        
    *   **Upstream Dependencies:** **Database** – to read necessary input data (price series, possibly historical signals). It uses env vars like DATABASE\_URL and strategy parameters: e.g. ORR\_OR\_MIN=5 (opening range window 5 min), ORR\_WINDOW\_MIN=60 (post-open window to monitor), and session times (SESSION\_OPEN\_UTC, SESSION\_CLOSE\_UTC) to know trading hours[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L170-L178). These guide the strategy logic on when to allow tickets. It depends on many internal packages: @prism-apex/strategies for the strategy implementations (OSB, VWAP first-touch, etc.), @prism-apex/rules and rules-apex for applying guardrails to each potential ticket (ensuring stops, R:R, drawdown rules, etc.), @prism-apex/ticketizer to format and write out the ticket entry properly, and possibly @prism-apex/consistency or risk-state to update any stateful aspects (e.g. tracking if the consistency rule might reject a trade). Essentially, it ties together all the logic packages to produce the final ticket objects. It also uses the Node pg library (same as API) to query recent bars from the DB.
        
    *   **Downstream Dependents:** The **tickets JSONL files** are the primary output for operator consumption (via the Dashboard or direct file reads). The **API** also relies on this output: when an operator requests tickets for today, the API serves what this job produced. Additionally, any **analytics or reporting** on historical performance would depend on the completeness of these ticket logs. There’s also a notion of “fanout” for multiple accounts (the ticketizer package’s fanout.ts suggests splitting a ticket for multiple accounts), meaning if an operator has several Apex accounts, the system can duplicate the ticket appropriately – this job likely triggers that logic so each account’s ticket gets recorded (the Dashboard Operator Console documentation hints at multi-account fanout[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/TECH-SPEC.md#L123-L125)). No other code calls this job; it’s either run on schedule or manually.
        
    *   **Stability:** **High criticality, moderate churn.** This is the **core of the trading strategy automation**, so it must be robust. As strategies are added or adjusted, this job will change – making it a point of expected churn when expanding functionality. However, it’s governed by strict rules: any change must preserve the guardrails. The risk of errors here is high-impact (a bug could generate an incorrect or rule-violating ticket). Thus, tests (including “golden sample” tests) should cover it[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/TESTING.md#L11-L19). Over time, new strategies can be added through configs without modifying this runner (it can dynamically load strategy definitions if implemented that way – _UNVERIFIED dynamic loading_). Still, introducing new strategies or guardrail logic means modifying this pipeline, which is a **high-risk change** (see Change Safety). We consider the existing two strategies and guardrails as stable reference implementations; adding more logic should be done carefully. The basic loop (run every minute) is stable, and performance needs to be maintained (running too slow could skip signals). Invariants (like never bypassing guardrails) must hold in every future revision.

4\. Build & Tooling Architecture
--------------------------------

This monorepo uses a **workspace-based build system** centered on Node.js and PNPM, with attention to consistent coding standards and CI efficiency. Key aspects of the build and tooling architecture include:

*   **Workspace & Package Management:** The repository is configured as a PNPM workspace (see pnpm-workspace.yaml[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/pnpm-workspace.yaml#L2-L6)), which includes all apps/\* and packages/\* directories as projects. PNPM ensures all packages can reference each other via the @prism-apex/\* aliases without publishing. Node.js v20 LTS is the target runtime[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/README.md#L509-L512), ensuring a consistent JS engine across development and production. Dependencies are locked via pnpm-lock.yaml for reproducibility. There is no evidence of a separate build tool like Nx; instead, PNPM’s native capabilities and some custom scripting orchestrate builds and tests.
    
*   **TypeScript Project References:** The repo uses a base tsconfig with path mappings[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/tsconfig.paths.json#L2-L10)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/tsconfig.paths.json#L28-L36) and likely project references to manage multi-package compilation. This allows incremental builds of only the packages that changed. Each package has its own tsconfig.json and output directory (dist). Most packages are compiled with plain tsc (TypeScript compiler) as indicated by their build scripts[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/packages/ticketizer/package.json#L18-L26)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/packages/rules/package.json#L19-L27), while the API uses a bundler (tsup) for its runtime output[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/AGENTS.md#L173-L180). The path aliases (like @prism-apex/app-api to apps/api/src) let packages import each other by logical name[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/AGENTS.md#L178-L183), and are honored in both build and test configurations via tsconfig and tooling (Vitest uses a plugin for this mapping[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/README.md#L13-L18)).
    
*   **Build Outputs:** Each package produces a dist/ with either CommonJS or ESM modules as needed. The API specifically is bundled into a single CommonJS file (apps/api/dist/server.cjs) using **tsup**[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/AGENTS.md#L173-L180) to make deployment easier. The front-end (dashboard) is built with Vite, resulting in static assets (likely in apps/dashboard/dist/). These outputs are then used in Docker images for runtime (the Dockerfile copies them). There's a top-level Makefile to streamline Docker Compose builds (e.g., make build triggers a no-cache rebuild of images)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/CONTRIBUTING.md#L44-L50).
    
*   **Task Orchestration & CI:** A combination of PNPM scripts and Makefile commands orchestrates tasks across the monorepo. For example, pnpm -r build would build all packages, but the Makefile and Docker build rely on multi-stage builds defined in the Dockerfile. In CI (GitHub Actions), the pipeline runs linting, type-checking, and tests for all projects[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/README.md#L461-L469). CI also enforces the critical guardrail that no disallowed broker APIs are present (failing if patterns like placeOrder are found in the code)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/README.md#L456-L464). Non-critical checks (lint, typecheck, tests) are run but not made blocking in CI (currently soft checks)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/README.md#L461-L469), although developers are expected to keep the codebase clean (noted that CI is non-blocking except the “no orders” rule[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/TESTING.md#L174-L182)).
    
*   **Testing Strategy:** The repo follows a **unified testing approach** for both front-end and back-end using **Vitest** (a Vite-friendly test runner) for TS/JS and **Pytest** for Python utilities[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/AGENTS.md#L122-L130). There is a mention of a "test pyramid" with unit tests, golden samples, and fixture-based I/O tests[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/TESTING.md#L11-L19). This suggests: unit tests for small functions (e.g., indicator calculations, guardrail checks), golden sample tests where a known input produces an expected output (useful for strategies or end-to-end flows), and possibly tests that use recorded data sets as fixtures to simulate a trading day. Vitest is configured to run tests in each package (see vitest.workspace.ts for combined config, possibly enabling multi-package test runs). The packages/ticketizer and others have their own test scripts (vitest --run which likely runs all tests once)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/packages/ticketizer/package.json#L19-L27). Tests can be filtered by project, e.g., pnpm test:api runs only API tests[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/AGENTS.md#L170-L174). The presence of apps/api/src/tests/... suggests the API has integration tests (like ensuring guardrails reject as expected)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/README.md#L50-L58). Overall, tests cover both logic in packages and the integration of those packages in the app. Python code (like scripts) have separate tests run via Pytest (likely minimal tests, as Python usage is limited).
    
*   **Linting & Formatting:** ESLint and Prettier are used to maintain code style and catch errors. The repo has a top-level .eslintrc.cjs and some overrides for specific parts (e.g. an override config for dashboard-lite). The ESLint config is “flat” and shared across workspaces[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/README.md#L509-L512). A pnpm lint will lint all projects. Prettier is included in dev deps for consistent formatting (likely invoked via ESLint or manually). The CI does run lint and typecheck (non-blocking currently)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/README.md#L461-L469), but developers are expected to fix issues regardless. Python code is linted/formatted with ruff and black[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/AGENTS.md#L123-L130), although Python code is sparse (mostly scripts). These are likely run locally or in a pre-commit hook (not certain if enforced in CI, but given the emphasis, probably yes as part of checks).
    
*   **Code Scanning & Dead Code:** There is a script for scanning the repo (e.g., scripts/scan\_repo.sh) and specifically a **depcheck** step (pnpm run scan:dead) that looks for unused dependencies[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/AGENTS.md#L123-L130). This helps keep the package.jsons tidy and catch any orphan code. The presence of a scan\_repo.sh suggests automated scanning for forbidden patterns (and indeed we know the CI greps for order placement APIs[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/README.md#L456-L464)). Also, cleaning scripts exist (e.g., cleanup\_repo.sh) to remove caches and cruft like .pytest\_cache/, .turbo/, etc., while protecting important directories[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/AGENTS.md#L14-L22).
    
*   **Build Caching & Performance:** The monorepo likely benefits from incremental builds due to TS project references – if you change one package, others don’t recompile. Additionally, tools like Vitest and Vite use caching to speed up tests and dev server. The Docker builds are multi-stage, which allows reusing layers between builds (e.g., dependencies installation layer, then build output). The CI might cache PNPM store and node\_modules to speed up install. We saw mention of .turbo/ cache directories[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/AGENTS.md#L19-L23), implying **Turborepo** may have been used or at least experimented with for task caching, but it’s unclear if it’s active. The dev workflow encourages using make up-dev for a quick start of just the UI in dev mode, separate from the full stack, which also implies building only what’s needed.
    
*   **Continuous Integration (CI):** The CI pipeline ensures code quality gates are run on each PR. As noted, any code introducing broker order calls fails CI hard[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/README.md#L456-L464). Other failures (lint, type, tests) do not block merge right now, but artifacts are uploaded for inspection[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/README.md#L461-L469). This indicates the team might allow interim issues but track them. However, developers are instructed to treat these as required (and indeed an onboarding step is to fix any lint/type issues)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/README.md#L442-L450). The server-up.sh script suggests deployment is done from a git clone at a specific tag, not necessarily pulling images, so CI may not push images to registry but at least confirms they build.
    
*   **Documentation Tooling:** The docs are kept in markdown and some are auto-generated or assembled from multiple sources (the presence of scripts/docs\_refactor.mjs and “auto-generated from existing repo docs” notes[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/TECH-SPEC.md#L2-L9)). This suggests there are tools to consolidate documentation for easier consumption. E.g., AGENTS.md and TECH-SPEC.md gather content from others. This ensures the documentation stays consistent and up-to-date as code changes (an important aspect of governance and onboarding).
    

In summary, the build architecture prioritizes **consistency, automation, and safety checks**. The reliance on PNPM workspaces and Docker means developers can emulate production closely (Docker Compose is used for all environments, avoiding “it works on my machine” issues). Caching mechanisms (PNPM, potentially Turborepo, and Docker layer caching) are leveraged to make CI and local builds faster. The combination of these ensures that even as the monorepo grows, build/test feedback remains reasonably quick and quality is maintained.

5\. Runtime Architecture
------------------------

This section describes how the system operates at runtime: what processes run, how they communicate, and how configuration and secrets flow into the running system.

*   **Application Entrypoints & Processes:** The system runs primarily inside **Docker containers** (even in local dev, Docker is preferred[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/README.md#L196-L204)). The main long-running processes are:
    
    *   **API Server (Fastify)** – Runs as a Node.js process listening on port 3000 (inside container). It is the central hub for operators to query data (health, tickets, etc.)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L61-L69). It starts up, connects to Postgres (using DATABASE\_URL), and keeps a connection pool open for queries. It likely also reads configuration (strategies and rules) on startup so it knows what to enforce. The Fastify server might also embed a WebSocket for live updates (not explicitly confirmed – but Fastify can do websockets; if implemented, the UI could connect to get push notifications of new tickets rather than polling).
        
    *   **Dashboard (Full) – Nginx + Static Site** – In runtime, the dashboard is served by an Nginx process inside the dashboard-full container[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L73-L81). Nginx serves the pre-built static files on port 80 (mapped to host 5180) and also acts as a reverse proxy for any API calls from the UI to the API server (the config likely forwards /api/ requests to api:3000)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/CONTRIBUTING.md#L39-L42). This means the browser can talk to the API through the same origin (the Nginx on 5180). The dashboard itself runs in the user's browser (React app executing in browser’s JS runtime).
        
    *   **Ingress (Yahoo)** – Runs as a Node process (likely using a minimal Express or just Node script) on port 8080 inside container[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L119-L127). At runtime, it establishes a connection to Yahoo data. This could be periodic HTTP fetches (e.g. every minute for new candle) or possibly a long-poll. Yahoo doesn’t provide true streaming WS for free, so it’s likely polling. The ingress writes data to Postgres – it will connect using DATABASE\_URL just like the API[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L52-L60). Because it’s under the local,prod profiles always, it’s a core part of runtime, ensuring continuous data flow. It also exposes /health which the docker healthcheck hits to confirm it’s working[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L122-L129) (maybe it returns 200 if it was able to fetch recent data).
        
    *   **Background Jobs (ingest-once, gapfill-once, tickets-once)** – These are ephemeral containers that run to completion for one-time tasks. For example, at startup make up will run ingest-once, gapfill-once, tickets-once in sequence to seed the system[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/Makefile#L34-L41). They run their Node scripts then exit. They are not long-running, but they can be triggered on demand (e.g., make seed). There are also scheduled variants:
        
    *   **Gapfill Cron** – An Alpine-based cron process that runs nightly at 02:20 UTC to fill any missing bars in DB[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L198-L206). It uses crond with a schedule that triggers a Node command to run the gapfill script inside the running API container context (using Docker exec)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L200-L208). This unusual setup (cron exec into API container) ensures if minor data gaps happened (e.g., slight downtime), they are backfilled daily. The gapfill-cron container itself is always on (restart unless-stopped), sleeping except at 02:20.
        
    *   **Tickets Cron (Real-time ticket runner)** – A container that continuously executes the ticket generation script in a loop[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L219-L228). At runtime, it waits for both API and DB to be up[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L229-L235), then every 60 seconds it calls node apps/tickets/dist/backfill-orr.js. In effect, this is a scheduler to run strategy checks each minute. The separation ensures that if the API is busy or down, the strategy loop can still run independently. It logs a line “\[tickets-cron\] running” each cycle for visibility[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L223-L228). This process is the heart of live signal generation.
        
    *   **Database (Postgres)** – Runs as a standard Postgres 16 server inside a container on port 5432, with its data persisted in a Docker volume (db\_data)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L2-L10). Other services connect to it over the Docker network (host mapped to 55433 for local access if needed). At runtime, it holds tables like bars\_1m, possibly tickets, and maybe configuration data (though config is mostly file-based, we do see maintenance SQL for vacuum in the db\_maint service).
        
    *   **db\_maint (Postgres maintenance)** – A cron job container (Alpine + crond) that performs a nightly VACUUM ANALYZE on the database at 02:00 UTC to keep it healthy[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L34-L42). It’s only enabled in prod profile, but it could run in local too if profile included. This ensures DB performance by reindexing and statistics update daily.
        
*   **Inter-Process Communication:** The architecture favors **shared data over direct RPC**:
    
    *   **Database as a hub:** The Postgres DB is a primary integration point. The ingress writes price data to DB, the strategy jobs read from DB, the API reads from DB to serve data (e.g., the /tickets endpoint might read from either JSONL or DB; bars endpoints definitely read DB)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/README.md#L488-L491). This decouples producers and consumers (ingress and strategies don’t call each other directly, they meet in the DB).
        
    *   **Files (JSONL tickets):** The ticket log is another medium of communication. The tickets-cron writes to tickets/\*.jsonl files, and the API simply reads those when serving ticket history[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/TECH-SPEC.md#L107-L115). The Dashboard indirectly gets that data via the API. Using the file ensures an append-only record and decouples generation from serving (the generator doesn’t need to call an API to post a ticket; it just writes the file).
        
    *   **HTTP/REST:** The only client-facing interface is the Dashboard calling the API’s HTTP endpoints. Within the cluster, the Dashboard container communicates to API (through Nginx or directly in dev). No other service uses HTTP to talk to API (no webhooks from internal services; e.g., ingress does not call API endpoints to push data, it writes DB directly). The healthchecks are one internal HTTP use: docker-compose health checks call API’s /health and ingress’s /health via HTTP locally to ensure readiness[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L62-L69)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L124-L129).
        
    *   **WebSockets/Eventing:** For external market data, Yahoo ingress might be polling. If we consider the “realtime services” enabled by enable-realtime.sh, it brings up gapfill-realtime and tickets-realtime services[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/tools/codex/enable-realtime.sh#L24-L32). Those likely connect to a web socket feed (perhaps from Tradovate, using “codex-governor” and “forcecurl” overrides to enforce certain network rules). _UNVERIFIED:_ We deduce that in a realtime scenario, instead of polling Yahoo, a direct Tradovate connection might be used by these realtime containers. If so, that data might bypass Yahoo ingress and go directly to strategy evaluation. However, currently, by default the system uses Yahoo delayed data and the realtime overlay is an optional add-on.
        
    *   **Process Coordination:** Docker Compose ensures dependencies: e.g., tickets-cron waits for API and DB (so it doesn’t start generating tickets before data is ready)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L229-L235), API waits for DB[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L56-L64), etc. The enable-realtime.sh script uses override compose files to start additional services, implying dynamic composition. This design allows toggling live vs delayed modes without changing code – by launching different supplemental containers that feed the same DB or share volumes. For instance, tickets-realtime might be a variant of tickets-cron that gets live ticks via a different mechanism.
        
    *   **Volumes & Shared Files:** A named volume api\_data is used to share data between containers, especially tickets logs. The API and Dashboard containers mount api\_data:/data:ro[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L70-L78)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L86-L90). The tickets-cron container does not explicitly mount api\_data, but writes to /app/apps/tickets/dist/backfill-orr.js (which writes to the default tickets location likely on the API container’s filesystem). There is some nuance: the tickets JSONL files reside in the repository’s tickets/ directory on the host (bound to ingress-yahoo at /app/tickets[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L116-L123)). *   **Configuration & Environment Variables:** The system is configured via .env files and JSON configs:
    
    *   **Environment Variables:** A file .env (or .env.docker) provides base environment values for local and production runs. For instance, DATABASE\_URL, LOG\_LEVEL, API\_BASE\_URL for the dashboard, credentials if any (but none committed; secrets must be filled in manually)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/CONTRIBUTING.md#L40-L48). The Docker Compose picks these up (the API service uses env\_file: .env[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L48-L56)). The separation of profiles allows using different .env for server vs local perhaps (the server-up script defaults to using .env with a given tag). The environment variables control critical modes like TICKETS\_ONLY=true and ORDERS\_DISABLED=true which are always set to enforce no real trading[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L52-L60). Also present are variables controlling strategy behavior (mentioned above: YAHOO\_SYMBOLS, ORR\_WINDOW\_MIN, etc.) which can be tuned without code changes by editing env or config files.
        
    *   **JSON Config Files:** These reside in configs/ and possibly in config/. For example:
        
        *   configs/strategies/\*.json define per-strategy parameters (like which symbols or time windows the strategy is active, risk settings per strategy, etc.). E.g., vwap-first-touch.json might include a flag to enable/disable it and any thresholds specific to it[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/TECH-SPEC.md#L62-L70).

The code in rules-apex likely reads this to decide which rules are active or what values to use.
            
        *   config/contracts-spec.json contains tick size/value and a verification flag per symbol[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/README.md#L410-L419). It’s updated when new symbols are added or verified by a human (there’s a tickSpecVerified field and metadata for reviewer[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/README.md#L410-L419)). This file is loaded by the shared/contracts module to inform both backend and frontend of contract specifications for PnL calc.
            
        *   Possibly config/.env.template or others for environment template. And apex/rules.json referenced in docs might actually be inside docs/compliance rather than a runtime config – the example suggests an array of rule definitions loaded by compliance tools[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/GLOSSARY.md#L65-L73).
            
    *   **Secrets:** The system architecture deliberately keeps secrets out of the repo (no committed API keys or passwords). For local dev, Postgres uses default credentials (apex/apex) which are in docker-compose. Real broker API keys (for Tradovate if used) would go in an .env that is not in git. The TRADOVATE\_TOKEN or similar would be needed for clients-tradovate but is not present in the public config, which implies these are added manually when deploying on a server (the documentation likely provided a TRADOVATE\_OAUTH\_SETUP.md for developers to set that up). So secrets management is manual, with .env and possibly Docker secrets if it were production (not explicitly shown).
        
    *   **Feature Flags:** Apart from environment toggles (like switching data source), there isn’t a sophisticated feature flag system. Instead, enabling/disabling strategies or rules is done via config files or env. E.g., to disable a strategy, an entry in its config might be set false. To run in “mock mode” (no DB), they have an alternate port 8000 for API and script dev\_api.sh which starts Fastify with an in-memory or stub DB mode[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/PORTS.md#L5-L10). That suggests the API can run with DATABASE\_URL pointed to a mock (maybe an SQLite or an in-memory array for quick dev). Indeed dev\_api.sh likely sets up API in "mock mode" on port 8000[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/PORTS.md#L5-L10). This is used for a faster dev loop without needing Postgres (useful if just working on the front-end with static fake data). So _Mock vs DB mode_ is a runtime switch controlled by env and how you start the API (the compose uses DB mode by default at 3000, the dev script uses mock at 8000).
        
    *   **Auth & User Management:** There is **no authentication layer** mentioned – presumably the tool is deployed in a controlled environment or local machine for a single operator, so the UI and API don’t implement login. Security relies on the fact it’s not exposed publicly (if it were, one might restrict by network or basic auth). In production scenario, they might deploy in a closed network or require VPN. But at the app level, there’s no user roles concept; everyone who can access the dashboard is an operator with full view. For now, that’s acceptable given limited scope (one operator or small team usage).
        
    *   **Permissioning & Boundaries:** The critical boundary is the **no-trade boundary**: the code never crosses from recommendation to execution. So there’s no code path that requires credentials to place orders (hence not storing such secrets). This simplifies runtime security but puts onus on the operator to use the trading platform manually.
        
*   **Failure Modes & Recovery:**
    
    *   If **API** fails (crashes or healthcheck fails), Docker Compose will restart it (it has no explicit restart policy in compose snippet, but we can assume the default or it can be added). The healthcheck ensures it only reports healthy when both /health and a basic route respond 200[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L62-L69). If API is down, Dashboard will show it as unavailable (and possibly cannot fetch new tickets). The tickets-cron depends on API’s health to start, but interestingly once started it doesn’t continuously depend on API (though in compose they kept dependency link). If API was down but DB up, tickets-cron could theoretically still generate tickets (since it only needs DB and file). Indeed, they likely made it depend on API just to ensure ordering at startup, not because it calls API. So signals might still be generated even if API is temporarily down, and they’d be written to file. When API comes back, the new tickets are there to serve. This is a resilient design: decoupling via files means generation doesn’t stall if API is restarting.
        
    *   If **Ingress** fails (e.g., Yahoo fetch error or crash), its healthcheck will fail and Docker will restart it (since restart: unless-stopped is configured[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L86-L90)). Data might gap until it recovers, but the gapfill job at 02:20 will patch it anyway. There’s also a postdeploy-gapfill.sh that can be run to fill any missing data on deployment[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/tools/codex/postdeploy-gapfill.sh#L56-L64)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/tools/codex/postdeploy-gapfill.sh#L69-L77). The system is designed to be tolerant to short data outages using these maintenance tasks.
        
    *   If **Tickets-cron** fails (maybe an uncaught error in strategy code), it will also be restarted by compose (restart: unless-stopped is set[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L232-L236)). However, if it keeps failing due to a logic error at a certain data condition, it could flap. There is no out-of-band alerting for that beyond logs. Operators would notice absence of new tickets or check container logs via make logs. Ensuring robust error handling in strategies (catching exceptions so they don’t crash the loop) is likely part of runtime architecture. Indeed, the entrypoint script for tickets-cron wraps the call in a || true to never propagate an error (so the loop continues even if one run fails)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L223-L228). This means a strategy error would log but the loop wouldn’t stop, which is intentional to avoid downtime.
        
    *   **Logging & Observability:** All services log to stdout (and Docker captures that). Logs are in JSON format where applicable (especially API logs are said to be JSON with no PII[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/TESTING.md#L141-L144)). This makes it easier to parse if needed. The operator likely watches logs via make logs. There’s mention of Slack/Telegram alerts in docs for certain events (like if system paused due to rule)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/GLOSSARY.md#L172-L180), implying the system might send notifications. However, such integration isn’t clearly implemented in code we saw; it might be aspirational or via an external script. Observability could be enhanced by the metrics endpoint if present (Prometheus could scrape if configured). But currently, the primary observability is through the Dashboard’s status displays (system health, alerts panel) and logs.
        

In summary, the runtime model comprises **multiple Docker-managed services** that communicate through the database, shared volumes, and HTTP, orchestrated by Compose. The design is **robust** in that the critical loop (data ingestion -> strategy -> ticket output) does not rely on a single monolithic service but is broken into self-contained pieces (which aids fault isolation and maintainability). Configuration is injected via files and env, making it flexible to change behavior without code changes (within the allowed range, e.g., enabling/disabling strategies, adjusting risk limits). The system is effectively event-driven on a 1-minute cycle: every minute, new data is ingested (Yahoo provides a new bar) and strategies evaluate; if a trade idea arises, it’s recorded as a ticket; the operator then manually executes and the cycle repeats. Outside market hours, the system mostly idles (ingress might still run if 24/7 data like crypto is included, but primarily it’s futures so overnight minimal activity except some suppression logic for EOD). By market close (EOD flat time), strategies auto-suppress new tickets[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/AGENTS.md#L109-L117), and an operator can be confident no further signals will come until next session. The **runtime architecture ensures compliance** at every step: no path exists to auto-execute trades, and guardrails are always applied before any ticket becomes visible[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/README.md#L20-L28). All state that matters (account state, last bar, etc.) is either in the DB or implied by log files, so containers can be restarted without losing the essential state (the only thing potentially in-memory is trailing drawdown high-water mark, but that likely is recomputed from DB equity history or could be stored in the DB by risk-state logic, _UNVERIFIED_ how exactly it's persisted). This stateless or minimal-state design aligns with using Docker Compose for horizontal parity between local and server – one can tear down and bring up the stack and it will rebuild state from DB and logs, making development and ops easier.

6\. Data & Integration Flows
----------------------------

This section follows the major data flows through the system and outlines integration points with external systems:

*   **Market Data Ingestion (Yahoo → DB):** The primary market data source is Yahoo Finance’s API (15-minute delayed feed for futures). The flow begins with the **Ingress Yahoo service** which periodically requests price data:
    
    *   **Initial Backfill:** On first run (or when seeding new symbols), the **Ingest job** (apps/ingest) fetches historical 1-minute bars for the past N days for each symbol[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L137-L145). It writes these into the Postgres database, populating the bars\_1m table (with columns like timestamp, open, high, low, close, volume, symbol). This provides the baseline history. This job uses @prism-apex/data-yahoo to get data from Yahoo’s REST endpoints[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L137-L145).
        
    *   **Realtime Updates:** The **Ingress Yahoo** container then takes over to keep data updated. Every minute (or whatever interval, default 1m), it queries Yahoo for the latest bar or quote for each symbol and inserts it into the DB. Because Yahoo data is delayed, this suffices for near-real-time strategy operation with a lag. No direct mention of how it handles volume or partial bars, but likely it waits for each minute to complete. If ingress misses any bars (due to downtime), the nightly gapfill will backfill them[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L198-L206).
        
    *   The data flow is one-direction: Yahoo → (HTTP/JSON) → Ingress service → (SQL INSERT) → Postgres. There’s no data sent back to Yahoo. The integration with Yahoo is purely reading public market data (no auth needed).
        
    *   **Data Schema & Ownership:** The bars\_1m table in Postgres is the central repository of market data. The schema includes a composite primary key (timestamp, symbol) or similar, ensuring uniqueness. The system expects this DB to be the source of truth for price series[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/README.md#L488-L491). The code that uses it (strategies) is responsible for interpreting it correctly (e.g., calculating ATR). There may also be a bars\_1d or other timeframe table for reference (though not indicated, perhaps 1m is sufficient and higher timeframe can be derived).
        
    *   Data retention isn’t explicitly addressed, but given the volume of 1m bars, storing indefinitely is fine for a limited set of symbols. If needed, older data could be archived, but likely not necessary until years of operation.
        
    *   **Integration Risk:** Yahoo’s API is external and can rate-limit or change. The system mitigates this by chunking requests (postdeploy-gapfill splits symbols into batches and pauses between them[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/tools/codex/postdeploy-gapfill.sh#L102-L111)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/tools/codex/postdeploy-gapfill.sh#L114-L123) to avoid hitting limits). Also, multiple attempts with backoff in gapfill suggests resilience to API failures[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/tools/codex/postdeploy-gapfill.sh#L50-L58)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/tools/codex/postdeploy-gapfill.sh#L114-L123). Yahoo data is not guaranteed, but since the stakes (demo trading) are okay with 15-min delay, it’s acceptable. If Yahoo fails or is insufficient, the architecture allows swapping in a new data source (even live feed) by adjusting the ingress service (like running compose.codex-governor.override.yml could attach to a different feed, presumably Tradovate’s).
        
*   **Strategy Evaluation (DB → Tickets):** Once data is in the DB:
    
    *   The **Ticket generator** (either tickets-cron or manual backfill run) queries recent bars from the DB for each active strategy. For example, OSB might query the day’s opening range (first N minutes after session open) for the symbol and see if price broke out later[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/AGENTS.md#L56-L64). VWAP strategy will fetch the current price vs VWAP computed over some window. The code uses @prism-apex/indicators to derive values like VWAP and ATR from those bars[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/README.md#L488-L491).
        
    *   Each strategy’s logic runs and produces either a proposed ticket (with side, entry, stop, target, etc.) or nothing if no signal. This is done in memory.
        
    *   The orchestrator then passes this proposal to **Guardrails enforcement**. Using @prism-apex/rules-apex, it checks the trade against all Apex rules[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/README.md#L32-L35):
        
        *   e.g., ensure stop-loss is present (if not, reject),
            
        *   compute risk-reward ratio and ensure it’s within min/max[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/TECH-SPEC.md#L72-L80) (if outside, mark not accepted),
            
        *   adjust quantity if needed (e.g., half-size if account is in drawdown buffer period[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/TECH-SPEC.md#L72-L80)),
            
        *   check trailing drawdown and daily loss from risk-state to ensure taking this trade wouldn’t break them,
            
        *   ensure time is not in EOD flat window (if it is, reject with reason EOD\_WINDOW[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/AGENTS.md#L109-L117)).
            
        *   All guardrail results are collated. The trade idea either passes all (accepted = true) or fails one (accepted = false). Reasons and hints (like sizingHint "half-size") are attached as metadata[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/AGENTS.md#L90-L98).
            
    *   The resulting **Ticket** (structured as per schema[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/TECH-SPEC.md#L82-L91)) is then persisted by the ticketizer:
        
        *   It appends a JSON line to the tickets/YYYY-MM-DD.jsonl file, including timestamp and all fields[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/AGENTS.md#L76-L84)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/AGENTS.md#L90-L98).
            
        *   It might also insert a record into a tickets SQL table (the presence of querying public.tickets in postdeploy-gapfill suggests such a table exists[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/tools/codex/postdeploy-gapfill.sh#L76-L84)). If so, likely the API or orchestrator does an INSERT as well. Keeping tickets in DB could facilitate easier queries and is consistent with grabbing symbols union from tickets table.
            
        *   If fanout is configured (say operator has 2 funded accounts), ticketizer might create one JSON entry per account (with same strategy and details, different accountId). In the example ticket JSON, accountId is part of each ticket[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/AGENTS.md#L80-L88). Possibly multiple accounts are comma-separated in config and ticketizer writes multiple lines for each.
            
    *   **Data Outputs:** The primary output is the JSONL log, which is considered canonical[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/README.md#L402-L406). This file is easily exportable (and indeed served via API). The DB table (if used) is secondary, perhaps used for internal calculations (like gathering all symbols in tickets for gapfill symbol discovery[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/tools/codex/postdeploy-gapfill.sh#L76-L84)). The JSONL is never edited, only appended; if a ticket is rejected, it still gets logged with "accepted": false and a reason (so operators see that a signal occurred but was not accepted due to guardrails[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/AGENTS.md#L115-L123)).
        
    *   **Operator Integration:** The end of this flow is the operator’s manual action. They monitor the Dashboard for new tickets. When a new ticket appears (say with accepted=true), they then go to Tradovate and manually place an order with the specified entry, stop, target, and quantity, using OCO (One-Cancels-Other) bracket orders[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/AGENTS.md#L22-L30)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/GLOSSARY.md#L160-L169). The dashboard’s Operator Console likely provides a convenient copy-paste format for these orders[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/TECH-SPEC.md#L123-L125). The operator can also see if any tickets were rejected (with reasons like "EOD\_WINDOW", which tell them the system skipped signals due to rules).
        
    *   There is **no direct Tradovate integration for execution**: the loop stops at providing the suggestion. The operator’s actions are outside the system boundary (except they might log something like marking a trade executed in an external sheet or just mentally).
        
    *   **Post-Trade Data:** If we wanted to track performance, ideally the system would know if a ticket was actually executed and what the outcome was. Currently, it doesn’t automatically know – that would require linking to Tradovate fills which is not implemented (no position tracking except via possibly reading account equity via Tradovate API). Instead, the operator can see PnL projections on open tickets (using target-stop vs entry) and after trade completion, presumably the operator would mark something manually. The system does not appear to ingest actual trade results, it only simulates in forward.
        
*   **External Integrations and Outputs:**
    
    *   **Tradovate (Broker) Telemetry:** As mentioned, there is a package for Tradovate client, possibly used to pull account info. If integrated, the flow could be: a background thread in API calls Tradovate REST to get current account balance, daily P/L, open positions, etc., and then updates the risk-state or an endpoint that the Dashboard displays (for example, "Account Balance: $X, Trailing DD remaining: $Y"). This would close the loop to some extent by confirming the operator’s manual actions reflected in the account. The _INTEGRATIONS-TRADOVATE.md_ likely outlines how to set up API access. If enabled, the account data might come into the API and be served via an endpoint like /api/account or included in the /ready status. The system’s design (with no orders) means Tradovate integration remains read-only. This is an asynchronous integration (poll every few seconds or on demand).
        
    *   **TradingView Webhooks:** The presence of webhooks.tradingview.ts suggests the API can accept incoming signals from TradingView (like custom alerts). If so, that is another integration: TradingView can send an HTTP POST with alert details, the API route parses it and potentially creates a ticket or at least a signal. If implemented, this effectively allows external signal sources. The @prism-apex/signals package would handle parsing those into internal format. This integration would mean the API is not purely internal – it needs to be accessible to TradingView’s webhooks (likely via a public URL or via tunneling). The system would treat those signals similarly to internal strategy output but possibly mark them differently. Because it's still tickets-only, the webhook would trigger the pipeline to produce a ticket (with accepted always false if it violates guardrails, etc.). This could extend the functionality beyond the built-in strategies. It’s noted as a likely integration but not deeply documented in our evidence (so it’s optional).
        
    *   **Slack/Telegram Alerts:** The Operator Handbook suggests the operator should ensure Slack/Telegram is connected for automated alerts[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/GLOSSARY.md#L140-L148)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/GLOSSARY.md#L172-L180). This implies the system might send messages when certain conditions happen (e.g., “System Paused: daily loss limit reached” or “New ticket generated: BUY MES @ ...”). If implemented, this would require integrating with Slack/Telegram APIs. Possibly a simple webhook out of the API or a script triggered by new tickets. We did not see explicit code for sending alerts (could be present but not obvious). If it's planned, an integration flow would be: API or a separate service monitors the tickets log or guardrail events and sends a message through a bot to a channel. This would be configured with a webhook URL or bot token (thus would be a secret in .env, which might be why those aren’t in public config). This integration is not essential to core function, but enhances usability by notifying the operator when away from the screen. For architecture: it’s an outgoing integration triggered by events (like on writing a ticket or on entering paused state).
        
    *   **Data Export & Analysis:** Operators or risk managers may want to analyze performance. The system provides **CSV export of tickets** via API[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/TECH-SPEC.md#L107-L115). The flow: when hitting /export/tickets?date=YYYY-MM-DD, the API likely reads that day’s JSONL file and converts it to CSV on the fly (through a simple transformation). The user can download this CSV for analysis in Excel or another tool. Additionally, because tickets are stored in JSON lines, one could ingest them into Python/pandas or any analysis program easily, outside the system. The team also has internal documentation and possibly runbooks for deeper analysis (like data-recovery-gapfill.md for recovering missing data). There’s no mention of an internal backtest module (there were hints of a backtest in docs, but not present in code, maybe removed or moved elsewhere). If they did want to backtest strategies on historical data, one could run the tickets job on historical DB data with accepted rules – essentially exactly what the backfill ORR does for last 30 days.
        
    *   **Infrastructure as Code Integration:** They provided systemd service example and Nginx config for production deployment. That suggests deployment integration: e.g., the team might use Ansible or manual steps to set up the server environment. Not exactly data flow, but integration of the application with the server environment (like using infra/nginx/setup-nginx-certbot.sh to enable HTTPS). In production, data like TLS certificates are managed outside the app (via Let’s Encrypt possibly through that script). The runtime uses those but not something the app code needs to know – Nginx handles TLS termination.
        
*   **Data Ownership & Persistence:**
    
    *   The **Postgres DB** owns historical market data and possibly tickets in structured form. It is persistent (with volume). Over time, that volume grows but likely manageable (1 minute bars for a handful of symbols is small). This data is crucial for strategy operation and can be considered the “memory” of the system. If it’s lost, strategies can’t compute properly (hence backups or at least the ability to re-run ingest needed).
        
    *   The **tickets JSONL** files are an append-only log that serve as an official record and for compliance. They stress to never delete these[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/README.md#L520-L523). Instead, if archiving, move them to an archive folder. This ensures an audit trail of all signals. Operators and risk officers must consider these logs immutable records. They might periodically back up the tickets/ directory to a safe storage (not described, but a prudent practice). Data in these logs is used for any post-hoc analysis or demonstrating compliance (like showing that every trade had a stop in the ticket).
        
    *   **Contracts spec JSON** (contracts-spec.json in config): Owned by the team’s analyst who verifies values. It’s updated manually when new instrument specs are needed and includes an audit field for reviewer and updated date[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/README.md#L410-L419). This file is read at runtime; if changed, one needs to rebuild the API (or at least restart it) for changes to reflect (though note that they mention after editing that file, run docker compose build api dashboard-full to propagate it[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/README.md#L430-L432)).
        
    *   **Log files:** Application logs stream to stdout, not stored persistently by the app. If needed, Docker or host can capture them. The cleanup script explicitly avoids deleting logs directories and files like \*.log outside the allow-list[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/AGENTS.md#L14-L23), so if any logs are written to files (e.g., the cron writes to /var/log/gapfill-cron.log inside container[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L200-L208) and db\_maint writes to /var/log/cron.log inside container[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L34-L42)), those persist only as long as container runs (which is restarted regularly for cron maybe, but those logs might not be easily extracted unless one execs in container). These are less critical.
        
*   **Known Data Workflows:** The documentation outlines specific flows:
    
    *   _Yahoo → DB → ORR → Tickets → Dashboard_[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/README.md#L479-L487): This is the core described above, confirming that no broker API feed is used (Yahoo delayed feed only)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/README.md#L479-L487) and that the outcome is tickets for manual execution.
        
    *   _Operator feedback loops:_ If an operator manually enters a trade, that action is outside the system, but its consequences (account balance changes) might reflect back via Tradovate telemetry if enabled. If not, the system only knows what it predicted, not whether it was taken or the result. Operators likely manually manage that (maybe by marking in dashboard if a trade was skipped or etc., though no mention of that feature; maybe they rely on consistent discipline that all “accepted” tickets should be taken).
        
    *   _End-of-Day (EOD) handling:_ At a set time before market close, the strategies auto-suppress signals (EOD flat requirement)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/AGENTS.md#L109-L117). The dashboard shows a countdown to that flat window[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/AGENTS.md#L113-L120). At EOD, ideally all positions should be closed by operator. The system doesn’t auto-liquidate (by rule). It likely doesn’t track positions to verify flatness, but the operator ensures it. Possibly the Tradovate integration could alert if any position remains near EOD (not sure if implemented).
        
*   **External System Limitations:** By using only delayed data and no order API, the system avoids regulatory or policy issues (Apex forbids automation). But it also means the system’s output might be trailing real-time a bit. However, since operators know it’s delayed, they can account for that (and the strategies are likely calibrated accordingly, maybe trading not ultra short moves that require split-second data). If a future integration to a real-time feed (like Rithmic or Tradovate’s live feed) is done, then the architecture can handle it by substituting the ingress. The codex realtime overlays indicate they prepared for possibly enabling a live feed with appropriate guardrails (“governor” might throttle or monitor the feed to ensure compliance).
    

In essence, data flows within Prism-Apex are designed to be **one-way and append-only for critical data** (market data flows in, trade suggestions flow out to logs). There is no feedback loop where the system changes strategy based on filled trades (no ML or adaptive logic, at least none mentioned). This simplifies validation and ensures all critical decisions are recorded and reviewable. Integrations are mostly about importing data (market prices, maybe account states) and exporting results (tickets, alerts) in a controlled, read-only manner, which aligns with the compliance-first approach.

7\. Deployment & Environments
-----------------------------

Deployment of Prism-Apex Tool is done via **Docker containers and Docker Compose**, aiming for parity between local development and production environments.

*   **Environments Overview:** There are mainly two environments considered:
    
    *   **Local Development** – Developers run the full stack on their machine with Docker Compose (or partially with dev scripts). Ports are exposed on localhost (e.g. API 3000, Dashboard 5180)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/README.md#L94-L102). Local env uses the same images (built locally) but can mount code for hot-reload or use special profiles for dev convenience.
        
    *   **Production/Server** – A server environment (could be a cloud VM or on-prem) where the tool runs for actual use by operators. This uses the compose prod profile which is very similar to local but possibly with some differences (like enabling the maintenance tasks, and presumably using real credentials in .env). In production, it might run continuously, possibly with systemd ensuring Docker Compose is up after reboots.
        
*   **Build Artifacts:** The deployment artifacts are Docker images:
    
    *   prism-apex/api:latest – contains the built Node API (and also includes code for jobs and possibly tickets generation since they share context)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L43-L51).
        
    *   prism-apex/dashboard-full:local (or a version tag) – contains the built static frontend served by Nginx[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L73-L81).
        
    *   prism-apex:ingress-dev – image for the Yahoo ingress service[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L110-L118).
        
    *   Possibly images for ingest and tickets jobs, but they actually reuse the api image by specifying target api in build and just giving a different image name (ingest:latest, tickets:latest)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L131-L140)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L162-L170). In practice, these might not all be pushed anywhere but built locally or on server.
        
    *   The use of multi-stage Dockerfile means a single Dockerfile in root likely defines how to build api target (compiling TS etc.), and how to build maybe a base image for running Node tasks. The apps/dashboard/Dockerfile is separate and likely uses a Node build stage to npm run build the React app and then an Nginx stage to serve it[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L73-L81).
        
    *   In CI, they might build these images on each push or at least on tagged releases. The server-up.sh script suggests that on the server, one would do git pull to a certain tag and then run compose to build and start containers[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/README.md#L130-L138). So perhaps images are not pulled from a registry but built in place. This is simpler for an internal tool (no heavy need for a registry unless scaling to multiple deploys).
        
    *   If they did use a registry, the image: prism-apex/api:latest hints at naming, but without a registry host, it's local. It might just be using the image name to tag local builds. The presence of specific tags (like local vs no tag) in compose suggests they differentiate between local dev images and release images. Possibly on the server, they set TAG env to a version (like v1.0.0) which might be used to pull specific images or checkout a tag.
        
*   **Deployment Process:**
    
    *   For local dev: Developer runs pnpm install, then either make up to start everything in Docker, or scripts/local-up.sh for a lighter weight dev approach (fastify on 8000 with hot reload and vite on 5173)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/README.md#L104-L113). They iterate, then make down to stop.
        
    *   For production: Steps from docs:
        
        1.  **Server Setup:** Install Docker + Compose V2, ensure ports 3000 and 8080 are free[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/CONTRIBUTING.md#L21-L29).
            
        2.  **Get Code:** Clone repo on server (likely a specific release tag).
            
        3.  **Configure Env:** Copy .env.template to .env and fill in secrets (like any Tradovate tokens if used, Slack webhook, etc.)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/CONTRIBUTING.md#L40-L48). Also, possibly adjust docker-compose.yml or overrides if needed for host specifics (but ideally not needed).
            
        4.  **Start Services:** Run make prod-up (which is docker compose --profile prod up -d)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/Makefile#L47-L55). This brings up db, api, dashboard-full, ingress-yahoo, gapfill-cron, tickets-cron, etc., all in detached mode. The Makefile then wires realtime if needed (calls enable-realtime.sh for prod, though that suggests if they want to enable the codex real-time feed, they can)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/Makefile#L48-L56), seeds initial data (make prod-seed)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/Makefile#L50-L58), and checks health.
            
        5.  **Access:** Operators then access the dashboard via the server’s IP or domain on port 8080 (which Nginx maps to 5180)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/CONTRIBUTING.md#L33-L41). The API is reachable at port 3000 (could be proxied by Nginx too under /api).
            
        6.  **Stop/Update:** To stop, make prod-down. To update to new version: pull new git tag, then run make prod-up again which will rebuild images if needed and recreate containers (with minimal downtime if done carefully).
            
        7.  They mention verifying health and endpoints after bring-up[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/CONTRIBUTING.md#L35-L43). Also, make prod-logs to tail logs and make prod-seed to reseed if needed.
            
*   **Environment Separation:**
    
    *   The Compose profiles allow running some services only in certain env. E.g. dashboard-dev service only runs in dev profile (used in dev environment to serve the UI via Vite)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L91-L99). For production, they don’t run that; they run dashboard-full with Nginx static.
        
    *   The dev profile (maybe used by make up-dev) runs the dev server for UI and perhaps a special file sync for tickets (orr-sync, tickets-sync in compose)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L237-L245)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L245-L254). These appear to mount volumes and run scripts to sync tickets file for front-end usage. This is a development convenience to allow the Vite front-end to read ticket data from the volume (or to continuously export latest tickets to some accessible place). Possibly in dev, they didn't want to write to host file, so they sync to allow the React dev server to pick them up. In any case, those dev-only services are not in production.
        
    *   There might also be a test profile (though not explicitly seen) for running tests in isolated environment (less likely as tests run via Vitest outside docker).
        
    *   The separation ensures that production runs minimal set (no live reload, etc.), and local dev can run quickly (no Nginx, no maint containers unless needed, etc.).
        
*   **Scaling & Performance:** The architecture is not aimed at high scalability (it's for a single user or small team). All components run on one server typically. If needed, one could separate database onto another host or run multiple API instances, but no such need now. The heaviest tasks are very manageable: a few strategies on 1m data for ~10 symbols is light. Postgres handles that easily, and Node handling at most a handful of HTTP requests (the UI polling or user clicking) and minute-by-minute tasks is fine. Memory footprints are modest. Docker allows pinning resources if needed, but default should suffice with a few GB of RAM.
    
    *   One potential heavy operation: initial ingest (downloading 30 days of 1m bars for 10 symbols ~ 1440 \* 10 \* 30 ~ 432k data points, trivial) and gapfill (similar scale if minor gaps). Strategy calc is also trivial at that scale. So performance is comfortable.
        
*   **Continuous Deployment:** Not fully automated from evidence. Likely manual: when ready to deploy new features, team tags a release in git, pulls on server, and restarts. Possibly could integrate with CI to build and push images, but that might be overkill for an internal tool. They specifically have docs to run on server with a clone, so probably no external registry push. So CI’s main role is testing, not deploying. Manual oversight is good given the critical nature (risk wants to approve changes).
    
*   **Infrastructure as Code:** Some is present: infra/nginx/prism-apex.conf.example suggests how to configure Nginx (maybe if running externally rather than inside Docker – but they do inside Docker for the app, though for TLS termination perhaps an external Nginx used). infra/systemd/prism-apex.env.example and maybe a service file likely for creating a systemd unit to run docker compose up on boot. They included setup-nginx-certbot.sh to automate LetsEncrypt certificate provisioning for the dashboard domain (which implies in production, they might run an external Nginx on the host for HTTPS, proxying to the internal Nginx or directly to API). Perhaps the production deployment uses the Docker Nginx for static content on port 8080 but to have HTTPS, they run another Nginx on host with certs and forwarding 443 -> 8080. It's plausible: the Compose exposes 8080, which is not default HTTP (maybe they intended to use 8080 behind a reverse proxy on 80/443). That might be due to port conflicts or leaving host 80 free for another service (like the ingress service is using host 8080 for itself, which is weird: Actually in compose they map ingress-yahoo 8080:8080 on host[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L120-L128) and dashboard-full 5180:80 on host[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L83-L90). So host 80 is free. They could have mapped dashboard to 80 but chose 5180, likely to avoid needing root or conflicting with a global web server. So, with their example, the user visits http://server:5180. But setup-nginx-certbot.sh might set up an Nginx on host to listen on 443 and forward to 5180 with TLS. It's somewhat redundant but plausible for adding TLS quickly without modifying Docker).
    
    *   There’s no mention of Kubernetes or cloud-specific infra; Compose is sufficient for single-machine deployment. That fits the scale and simpler ops model.
        
*   **Rollout and Rollback:**
    
    *   To upgrade, because stateless containers and volumes are used, one can do a rolling restart:
        
        *   Stop tickets-cron to pause generating signals,
            
        *   bring down API and others,
            
        *   update code/images,
            
        *   bring up and seed quickly,
            
        *   and resume tickets-cron.In practice, they might just do docker compose down && docker compose up -d quickly off-market hours (like after trading day).
            
    *   If an upgrade fails or introduces a bug, **rollback** is simple: checkout the previous tag and docker compose up that. Because data is stored in volumes and unchanged, the old version will pick up from DB and logs as if nothing happened. Ticket JSONL files will have continuous records (though any bad tickets from the faulty run remain in log but could be marked by accepted=false or by timeframe).
        
    *   They have a VERSION file in repo (saw in search) which likely marks current version. They might incorporate that into API’s /version endpoint (so operator can see which version is running).
        
    *   For minor config changes (like adjusting a strategy parameter), they can just edit the JSON config and restart the affected service (maybe just the tickets-cron or API if it caches config). Actually, since strategies might load config each run, possibly no restart needed if they programmed it to reload daily or on each evaluation (not sure). More likely, they read strategy config at start of each trading day or when the schedule says to switch strategy. There is mention of schedule in simulate\_strategy\_day.py (which loads a schedule presumably from config)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/scripts/simulate_strategy_day.py#L7-L15). Possibly the orchestrator re-reads schedule each day. But for a config change like risk limit, safer to restart to ensure all in-memory states reflect it.
        
    *   The system is not 24/7 critical (only runs during market hours typically), so deploying updates off hours is feasible.
        
    *   They stress to “install Docker to run containers” and the flows reuse existing scripts, meaning no new workflows to learn for deployment, it’s the same commands as dev (just different profile)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/README.md#L130-L138). This consistency lowers risk of deployment errors.
        

Overall, deployment is straightforward due to containerization. By encapsulating everything in Docker, the “it works on dev, not on prod” issues are minimized. The monorepo approach ensures compatibility among components for a given version. They do caution that the codebase might contain pre-existing minor failures but CI will alert (non-blocking)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/AGENTS.md#L160-L164), so perhaps they sometimes deploy even if not 100% passing (except order guard). That suggests a pragmatic approach but ideally they fix them eventually.

One critical **safety** deployment mechanism: the CI’s **no-order placement guard**. That ensures no code slip through that could auto trade. Even in deployment, if someone accidentally introduced such code and tries to deploy, CI fails so they likely wouldn't deploy it. This acts as a last line of defense in release process, aligning with risk-averse deployment.

Finally, they treat **Tickets and config as persistent state** to be preserved on deployment. The Compose and volumes reflect that (no container wipes the tickets/ or db\_data volume on re-run, so data persists across upgrades). The cleanup scripts explicitly avoid deleting those. This means older records accumulate (which is desired for audit). If log size becomes an issue, they might archive older JSONL to e.g. tickets/archive/ with date, but with careful coordination to not lose them.

In summary, the deployment strategy emphasizes **reproducibility, quick recovery, and compliance**: using Docker for reproducible env, not automating order execution to avoid irrecoverable mistakes, and maintaining logs for any needed rollback or audit. Environments are kept as similar as possible to avoid surprises when moving from dev to prod. Manual control over deployment (with documentation) ensures the risk officer or lead engineer oversees changes to this sensitive system.

8\. Cross-Cutting Concerns
--------------------------

Several important concerns span across multiple parts of the system, influencing the architecture and implementation globally:

*   **Observability (Logging & Monitoring):** The system produces structured logs for key events. All Node services (API, strategies) log in **JSON format** with no personal data[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/TESTING.md#L141-L144). This consistent JSON logging means they can be aggregated or searched easily (though currently likely just checked manually via docker compose logs). Health endpoints (/health, /ready) provide insight into service status for both humans and automated checks[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/README.md#L198-L204). The readiness check ensures dependencies (like DB connection) are up before marking ready[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L62-L69). There is mention of a metrics endpoint being present[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/TESTING.md#L141-L144), implying the API might expose runtime metrics (which could be instrumented by @prism-apex/metrics). If fully implemented, that could allow integration with Prometheus or a simple curl to get internal counters. Additionally, the Dashboard’s SystemStatus component likely queries health and readiness and maybe shows if something is wrong. For external monitoring, they likely rely on manual observation (no explicit integration with paging or such given the small scale, aside from Slack alerts for certain events as described). The architecture’s use of Docker healthchecks for services like DB and ingress provides self-healing triggers (restart containers if unhealthy for too long).
    
*   **Error Handling & Resilience:** The design anticipates possible error scenarios:
    
    *   Data ingestion and strategy execution are decoupled, so a failure in one doesn’t crash the entire system. For example, if the strategy code throws an exception for a symbol, the tickets-cron script catches it and continues the loop[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L223-L228) – preventing a single bad data point from halting all signals.
        
    *   Guardrails serve as not just business rules but also an error containment: e.g., if for some reason a strategy generated a wildly unrealistic target price, the R:R guardrail would reject it, preventing potentially dangerous advice from reaching the operator[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/TECH-SPEC.md#L72-L80). So guardrails double as sanity checks.
        
    *   The system is stateless between cycles (except DB state), so any crash and restart means at most missing one cycle. The gapfill and design of quick container restarts mitigate that.
        
    *   **Idempotency:** The docs mention “idempotent signal handling”[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/AGENTS.md#L10-L17) – meaning if the same signal triggers multiple times, the system should handle it once. The strategies likely are written to avoid duplicate tickets (or the orchestrator might mark that a ticket for a given strategy+symbol already exists for the day, etc.). Also, the design of writing to file and possibly checking if an identical line exists could avoid duplicates (though not explicitly described, but idempotency is a stated aim).
        
    *   **Pausing Conditions:** The system will halt generating new tickets under certain risk conditions (like daily loss halt)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/AGENTS.md#L14-L17). This is implemented in guardrails (if trailing drawdown or daily loss exceeded, guardrails reject all new tickets with a code). That effectively pauses the strategy output. An operator alert is supposed to be issued via Slack/Telegram in that event so they know to stop trading[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/GLOSSARY.md#L172-L180). This cross-cutting concern ties risk detection in code to operator procedure.
        
    *   **Consistency & Time Coordination:** All components use UTC time and configured session times to coordinate actions (ingestion, strategies, EOD logic) – time handling is consistent and config-driven (session open/close in env)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/docker-compose.yml#L172-L180). This ensures, for instance, that both strategy suppression and operator guidance (countdown timer) use the same notion of EOD time.
        
    *   The code likely uses library for time or careful handling to avoid timezone issues. The provided times are in UTC to avoid daylight savings confusion.
        
*   **Security Boundaries:** The primary security principle here is **no crossing of automation into execution**. This is reinforced through:
    
    *   **Code guards:** CI scans code for any reference to functions or APIs that would place or manage orders[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/README.md#L456-L464). This is an architectural invariant: it prevents even a well-meaning developer from accidentally incorporating an auto-trading library. In runtime, this means even if the system had credentials to broker API (which it typically doesn’t, since not needed), it never calls those endpoints.
        
    *   **Network isolation:** By running everything in Docker on a single host and not exposing the API to public (except via perhaps a secure channel for UI), the attack surface is small. The API doesn’t implement authentication, but presumably the deployment is such that only trusted users can connect (e.g., the server might be on a VPN or local machine).
        
    *   **CORS & Access Control:** The API has CORS allow-list via env[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/TESTING.md#L141-L144), meaning it will only respond to requests from the known dashboard origin, preventing random websites from hitting it. This is a security measure to avoid cross-origin calls except from the official UI.
        
    *   **Secrets:** The architecture keeps secret keys out of code. Any integration requiring auth (Tradovate, Slack) requires env variables that are not in the repo. This prevents accidental leakage of credentials and ensures they can be rotated or omitted as needed without code changes.
        
    *   **Principle of Least Privilege:** The system collects only what it needs. It does not, for example, store personal information about the operator or any unnecessary data. Even when connecting to Tradovate for telemetry, it only reads data. Thus, if compromised, the system cannot execute trades or withdraw funds. The worst-case breach impact is someone seeing the trade signals or possibly manipulating them (but if guardrails are intact, they'd reject out-of-line suggestions).
        
    *   There is no user accounts system or database of users, eliminating an entire class of security concerns (no login, no role permissions to manage beyond what's implicit: e.g., if multiple operators, they'd all see the same signals; the system isn't multi-tenant).
        
*   **Scalability & Coupling:** Shared abstractions and dependencies are carefully managed to prevent tight coupling:
    
    *   The use of local PNPM packages encourages reuse without duplicating code, but one must ensure not to create circular dependencies. The actual dependency graph is kept mostly one-directional (we saw e.g. ticketizer depends on accounts and rules, but accounts and rules do not depend on ticketizer – good separation).
        
    *   The architecture distinguishes clearly between strategy logic, guardrail logic, and execution pipeline, each in separate packages, which reduces coupling. Strategies only produce an ideal trade; guardrails independently validate it; ticketizer independently records it. This separation means changes in guardrails (like tightening a rule) doesn’t require changing strategy code; it just filters results differently. Similarly, strategy changes don't alter guardrail code.
        
    *   However, some coupling is inevitable: e.g., if a strategy is too wild, it relies on guardrails to catch it. They mention “danger zones: any code path that mentions placeOrder etc. must remain disabled or guarded”[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/AGENTS.md#L7-L15). This indicates they might have legacy code (maybe from algorithmic trading experiments) that could place orders, but they guard it with flags. That is a cross-cutting concern: ensure any such code is inert. Possibly in clients-tradovate or somewhere, they have stubs for order placement (if originally derived from a sample), and they put conditions if(ORDERS\_DISABLED) { throw Error } or similar. CI scanning those keywords is an extra layer. So they deliberately allow some code to exist (maybe for future or for partial integration) but guard it strongly at runtime and CI.
        
    *   **Shared modules risk:** The shared package introduces coupling in that both front and back rely on it (for contract specs and any utils). If someone changes contracts-spec.json structure or the parser in shared, both front and back must update. They mitigate risk by instructing to always update tsconfig paths if any folder moves[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/README.md#L14-L18), implying they pay attention to these shared boundaries. Also, they likely write tests for shared components that ensure consistency (like a test that a known contract-spec yields correct PnL output).
        
    *   **Implicit Contracts:** One example is the structure of ticket JSONL – it is an implicit contract between the generator and the Dashboard (and any analytics). It’s documented in multiple places[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/TECH-SPEC.md#L82-L91). Changing it would break things. They manage this by not changing it lightly and by documenting it clearly (so everyone writing code around it knows what to expect). Another implicit contract is how account state is interpreted across modules; the compliance engine expects certain fields (balance, trailingDrawdown, etc.) to be present. These are defined likely in accounts and must be consistently populated (via Tradovate API or config).
        
    *   **Testing Coupling:** They note “CI runs are non-blocking except for no-order-API guard”[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/AGENTS.md#L160-L164), implying sometimes tests or typechecks might fail but they still merge. This is a risk to consistency, but perhaps these are minor issues (like an unused variable or an easily spotted small test failing). It's a conscious decision maybe due to time constraints. However, letting such things accumulate can cause cross-cutting issues (e.g., unused dependencies might hide a misconfigured import). The architecture has a built-in check for dead dependencies to catch leftover couplings[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/AGENTS.md#L126-L130). They encourage running pnpm run scan:dead regularly. This is an unusual but interesting cross-cutting concern: **code cleanliness** as part of architecture governance. They explicitly include it in quality checks, meaning maintaining a tidy dependency graph and removing dead code is part of the architectural discipline.
        
*   **Security & Safety Recap:**
    
    *   The **hard security boundary** is that no credentials for trading are used and no direct external commands are executed. This drastically limits potential damage from any bug or compromise. In the worst case, the system could fail to alert or give a wrong suggestion, but cannot directly lose money because execution is human. This is an architectural trade-off (autonomy vs safety) made upfront.
        
    *   Another security layer is the "Absolute rule" in code: **never introduce broker order placement** and CI enforcement of that[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/TESTING.md#L180-L184). This is repeated in docs and is ingrained in team culture as well. It’s not just a technical enforcement but an organizational policy (non-negotiable).
        
    *   They also caution about platform compliance like “monitor for unauthorized API connections” in context of Rithmic/Ninja integration[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/TECH-SPEC.md#L170-L177), meaning if in future they connect to a platform that _could_ trade, they must be vigilant not to allow it to. So cross-cutting thought is given to every integration to ensure it doesn’t inadvertently allow auto-trading. For example, if they integrated NinjaTrader, they’d keep it read-only or at least have audit logs if any automation is tried.
        
*   **Shared Abstractions & Coupling:**
    
    *   **Examples of beneficial abstractions:** The reuse of the same code for data ingestion in both initial backfill and nightly gapfill ensures consistency (no two different ways to fetch data). The data-yahoo package is one abstraction for all Yahoo data operations, reducing duplication.
        
    *   **Examples of potential foot-guns:** If a developer were to bypass the ticketizer and write directly to the JSON file differently, that could break format expectations. Thus, they likely instruct to always use the ticketizer library for any code that outputs tickets. This is an implicit guideline: do not duplicate logic for writing tickets or applying guardrails outside the canonical modules. Changes should go through those modules to maintain consistency.
        
    *   Another foot-gun: directly querying DB for positions or calculating something that the guardrail logic also calculates differently. That could cause mismatch. They solved this by having one place for risk calculations (risk-state) and ensuring any other part uses that or its results rather than doing its own math.
        
    *   **Cleanup & Technical debt:** They have documented cleanup procedures and scan reports[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/README.md#L442-L450). They consider leftover clutter (unused files, etc.) as a risk (because it could confuse or mask issues). So they actively manage that cross-cutting via scripts and documentation steps.
        
*   **Compliance:** It’s worth noting that compliance with external rules (Apex’s rules) is itself a cross-cutting requirement. It affects how strategies are coded (they might consciously limit strategies to avoid styles that would conflict with rules), how guardrails are implemented (configurable and enforced globally), how operators use the tool (never rely on tool to auto-protect them beyond guardrails in code), and even how code is written (no circumventing guardrails). The entire architecture is shaped around compliance (the “tickets-only brain” motto[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/README.md#L473-L480) is essentially saying compliance is built into design). So compliance is not an afterthought; it’s a first-class concern that informs module boundaries (notice a whole package for rules-apex and a separate one for compliance checks in docs, etc.).
    

In summary, cross-cutting concerns are **well recognized and managed** through both code and process: Observability through structured logging and health checks, error resilience via decoupling and guardrails, security via strict no-autonomy boundaries, and an emphasis on maintaining a clean, consistent codebase to prevent subtle bugs. The architecture is strongly aligned with the overarching requirement of **no-regrets safety** – they would rather have a missed trade than an incorrect or dangerous trade, hence all these safeguards. This prudent approach might sacrifice some performance or convenience, but ensures reliability and trustworthiness of the system, which is paramount for its users (who need to trust that every ticket shown is vetted and meaningful).

9\. Change Safety Model (CRITICAL)
----------------------------------

Not all changes to this monorepo carry equal risk. This section delineates what kinds of modifications are low-risk vs. high-risk, and highlights areas with hidden blast radius or known pitfalls, so engineers can gauge the impact of their changes:

*   **Low-Risk Changes:**
    
    *   _UI and Documentation Updates:_ Modifying the Dashboard UI (e.g., changing layout, text, or purely visual components) or updating markdown docs is generally low-risk. These don’t affect the core trade logic or guardrails. For instance, tweaking a table format in the dashboard or improving log output formatting won’t impact trade outcomes (just verify UI still builds and displays).
        
    *   _Self-contained Package Additions:_ Adding a new package or module that doesn’t integrate deeply with existing flows is low-risk. For example, if we introduce a new analysis tool under packages/analytics that is not yet used by production code, it can be done with minimal fear of regressions (just don’t accidentally import it into critical paths). Such changes should still be marked experimental until proven.
        
    *   _Non-critical Refactoring:_ Cleaning up dead code, renaming variables for clarity, or splitting a large function into smaller ones, **provided tests remain green**, is low-risk. E.g., refactoring packages/indicators internals for clarity – as long as outputs remain the same (ensure via unit tests), the strategies using it won’t know the difference.
        
    *   _Configuration (Non-boundary) Adjustments:_ Changing values in config files (like adjusting a strategy parameter, or updating contracts-spec.json tick values after review) is low-code-risk (no code change), but note it can affect behavior. Within reason (e.g., raising a profit target threshold slightly) it’s considered low-risk to system stability – though it’s a **business risk** to be separately validated. Config changes should be reviewed by subject experts, but from an architecture perspective they are isolated and easily reversible (just change the value back).
        
    *   _Adding New Strategies (phased):_ Introducing a new strategy in the packages/strategies library can be done in a low-risk manner **if it’s initially disabled**. For example, you can implement strategyXYZ.ts, add its config (with "enabled": false), and deploy. Since it’s off, it won’t affect current operation (besides occupying some CPU if accidentally run, so double-check the orchestrator respects the config). This allows deploying code in phases: first deploy the code disabled, then later enable via config once tested in production environment with no surprises. This phased rollout (dark launching) is low-risk.
        
*   **High-Risk Changes:**
    
    *   _Guardrails or Rules Modifications:_ Changing anything in rules or rules-apex is high-risk. These are the core safety nets; any alteration can have broad consequences. For instance, if you loosen the Risk:Reward clamp or adjust trailing drawdown logic, you might expose the system to trades that were previously blocked (increasing risk), or conversely, you might over-block trades (reducing system performance). The blast radius is system-wide – it affects every ticket generation. Moreover, errors here can violate Apex compliance (worst-case, produce a ticket that breaks funding rules). Therefore, treat guardrail logic changes as **architectural changes** requiring thorough review, test against known scenarios, and possibly sign-off by the risk officer. Such changes often need to be rolled out during a simulation or test period, not directly in live trading.
        
    *   _Strategy Core Logic Changes:_ Modifying the behavior of an existing strategy (e.g., altering how VWAP first-touch identifies an entry) is high-risk. While this doesn’t violate compliance (guardrails still catch extremes), it can significantly alter trade frequency or profitability. A bug in strategy logic might produce a flood of bad signals or none at all. The effect is immediately visible to operators. Also, strategies often have subtle dependencies on data (like assuming certain bar intervals or times). Changing them could break those assumptions. Always accompany such changes with backtesting or sandbox testing. Ideally, use feature flags or config to turn new logic on gradually (for example, introduce a config flag “useNewAlgo”: false that you can toggle after deploying the code). If something goes wrong, be prepared to revert the change or toggle it off quickly.
        
    *   _Database Schema or Data Handling:_ Changing the structure of the Postgres schema (e.g., renaming a column, or switching how data is stored) is high-risk and tricky. The running services expect certain tables/columns. For example, if one alters the bars\_1m schema or how tickets are stored in DB, the ingestion and orchestrator code must be updated in lockstep. Migrations would be needed to transform existing data. A mismatch could cause runtime errors (e.g., strategies failing to query data) that are not easily caught by unit tests because they involve integration with the DB. Such a change can have non-obvious blast radius: it might break only at runtime when a specific query fails. Approach any schema change with caution: write migration scripts, update all code references, test thoroughly in a staging environment with a copy of the data. If possible, avoid schema changes that aren’t absolutely necessary. (So far, the design hasn’t needed dynamic migrations; introducing them adds complexity.)
        
    *   _Cross-Package Contract Changes:_ Altering the “contract” between modules (for instance, the shape of the Ticket JSON, or the interface of an indicator function) is high-risk. Many parts assume this contract. Changing the ticket format (say adding a field or renaming one) will affect the ticketizer, the API endpoints, and the Dashboard parsing/exporting – a broad blast radius. Similarly, if you change something like how AccountState is defined (in accounts package), the compliance engine, risk-state, and any Tradovate integration must adapt in tandem. These changes can break things subtly if any part is missed. They should be done only with comprehensive understanding of all consumers of that contract. If undertaken, ensure to update all dependent code, adjust tests, and likely plan a **coordinated release** where back-end and front-end are deployed together (since e.g., a front-end expecting accepted: true/false would break if you removed that field). Mark such changes as requiring a version bump or backward compatibility handling (maybe support both old and new fields for a while).
        
    *   _Bypassing Architecture Boundaries:_ Introducing changes that violate the established layering – for example, making the Dashboard fetch data directly from Postgres, or making a strategy function call out to external services – would be high-risk and generally a bad idea. This breaks the encapsulation and can create non-obvious blast radius. For instance, if a strategy tried to call Tradovate’s API to get some live data on the fly, that could slow down ticket generation or cause failures if Tradovate is down, and also violate the principle of single source of truth (since strategies should rely on our DB feed, not directly external feed, to ensure coherence). Another example: if someone thought to "improve performance" by letting guardrail code directly modify a ticket instead of going through ticketizer (maybe to save a write step), that could break invariants (like logs out of sync with memory). It's critical to respect the boundaries: all trades go through guardrails -> ticketizer -> log; all data flows through DB etc. Bypassing them is a foot-gun with complex side effects.
        
    *   _Removing Safety Checks:_ Any change that removes or disables an existing safety mechanism is extremely high-risk. For instance, comment-out the code that filters out placeOrder calls in CI or disabling the guard that ensures TICKETS\_ONLY mode in the API would be catastrophic – it undermines fundamental guarantees. Even if done for a test, it must never reach production. If there’s pressure to enable some form of automation (say, maybe someone suggests “let’s auto-submit orders just for testing”), treat that as a major architectural decision requiring approval at the highest level (and likely will be rejected given non-negotiable policy[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/TECH-SPEC.md#L28-L36)). The known architectural foot-gun here is accidentally introducing order placement code or enabling it – the CI and code flags are specifically to prevent that. So never remove those safeguards without explicit, deliberate architectural revision and acceptance of the enormous risk (which currently is off-limits by policy).
        
*   **Blast Radius Awareness:**
    
    *   Some parts of the system have a **non-obvious blast radius** if changed. For example, altering the **port numbers or compose profiles** seems simple but can confuse developers and operators (the docs and scripts rely on canonical ports[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/PORTS.md#L5-L10)). Changing a port in code means updating multiple docs, health checks, maybe firewall rules. Similarly, updating a library version might seem isolated but could break our builds or runtime in subtle ways (e.g., updating pg library version – should be fine but if config changed default SSL behavior, could break DB connection).
        
    *   The coupling between **Dashboard and API** means any change in the API data model or endpoints can break the UI. Always consider: if I change this output, what will the front-end do? The team is likely to deploy front-end and back-end together (monorepo helps), but sometimes an operator might open an older cached version of the dashboard with a newer API or vice versa. So ideally maintain backward compatibility or versioning on API if breaking changes are needed.
        
    *   The **accounting and risk modules** (accounts, risk-state, consistency) have a broad effect: they feed into both guardrails and UI. If you tweak how trailing drawdown is computed in risk-state, ensure the UI’s display of trailing drawdown corresponds (if the UI displays that at all). A mismatch could lead the operator to wrong conclusions (UI might say you have $500 buffer but a changed risk-state might trigger half-sizing earlier). Thus, changes in these modules need synchronization with everyone’s understanding and possibly UI hints.
        
    *   **Tooling changes** (like changing the build process or CI config) can also be riskier than they appear. For example, switching from tsup to another bundler for API might introduce subtle runtime differences. Or tightening lint rules might suddenly break pipelines or cause developers to spend time fixing style instead of features (not a runtime risk, but affects dev velocity). Evaluate these in context: they might require all devs to update their environment or retrain. Such changes should be communicated and perhaps tested on a branch first.
        
*   **Known Foot-Guns (Known issues or tricky areas):**
    
    *   The user mention in docs that the codebase _“may contain pre-existing lint/typecheck/test failures”_[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/AGENTS.md#L160-L164) suggests that there are some minor issues already present. A developer might think “I see a failing test, I’ll fix it.” But caution: maybe that test fails because of an environment issue or a known non-critical bug the team hasn’t resolved yet. Fixing it is good, but ensure you understand why it was failing. Perhaps the fix is non-trivial or the team intentionally left it because it doesn’t affect production (though ideally all tests pass). This is a minor foot-gun: don’t assume all failing tests are up-to-date; check if they’re known issues (maybe documented in REPO\_SCAN\_QUESTIONS.md).
        
    *   Another foot-gun: forgetting to update **paths or config** when moving files. The docs explicitly say update tsconfig paths if moving files[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/README.md#L14-L18). If you reorganize packages or rename something, missing a reference in tsconfig or compose file can lead to things compiling but not working at runtime. Always search the repo for old names after such changes. This monorepo relies on these mappings, so one missed mapping update can break imports at runtime in subtle ways.
        
    *   **Race conditions:** The system is largely single-threaded (Node) and sequential (cron loops), but consider interactions like: If you run make up and it seeds data and immediately starts tickets-cron, could tickets-cron attempt to generate a ticket before ingest-once has finished populating the last few minutes of data? Possibly the sequence in Makefile avoids that by running seed fully then tickets-cron. But if one manually runs things in wrong order, you could have a situation where strategy didn’t have data and skipped a signal. Not a huge issue, but something to be aware of if changing startup sequence.
        
    *   **Time zone and scheduling foot-gun:** The schedules and EOD suppression rely on configured times (UTC in env). If someone changes the trading session times (say to test on a different market), they must update in multiple places (session open/close, perhaps the dashboard countdown code). Missing one could cause, e.g., strategies not suppressing when they should. So treat any change to schedule or timezone as risky, test thoroughly across a day’s cycle.
        
*   **Mitigation Strategies:**
    
    *   For any **high-risk change**, perform it in a feature branch and use the extensive test suite (and add tests for new edge cases). Spin up a staging environment if possible: e.g., run Docker Compose with the new code feeding a test database and ensure outputs look sane. For guardrails and strategy changes, consider doing a **replay test**: run the tickets backfill job on historical data with both old and new code and compare outputs. Differences should be understood and agreed upon.
        
    *   Classify each change’s risk up-front (like we are doing here) and discuss in PR reviews. The team should be extra cautious on any code in rules\* and tickets path.
        
    *   Maintain a **rollback plan** for every deployment: if we push this change and see problems, what exactly will we do? For example, “if new strategy outputs too many tickets, we will immediately disable it via config and redeploy, or revert to previous commit.” Because the system has manual oversight, an operator might catch issues – ensure they know how to respond (maybe an internal runbook: “if system behaves oddly after an update, toggle strategies off or stop tickets-cron and notify dev team”).
        
    *   In code, use _flags or config toggles_ to isolate risky changes. Instead of outright replacing an algorithm, you can introduce a config flag (default off) for the new behavior, run it in parallel logging maybe debug info, and then later switch it on for all. This incremental approach limits blast radius initially.
        
    *   Communicate with the **Risk Officer** (which in context might be the user or a role the user is playing). Some changes, particularly guardrails, likely require sign-off from the risk perspective. E.g., “We plan to raise max risk:reward from 2:1 to 2.5:1 to allow more trades – approve?” That should be documented and approved outside of code review alone.
        
    *   Be aware of the **non-obvious impacted areas** by thoroughly searching the code for any references to what you’re changing. If changing Ticket structure, search the whole repo for accepted or whatever field to find where it's used (Dashboard, tests, etc.). Our monorepo and tests help here because everything is in one place.
        
*   **Summary of Risk Levels:**
    
    *   **Low risk:** Pure UI tweaks, documentation, adding inactive features, internal refactors that pass tests.
        
    *   **Medium risk:** Changes to strategy code (but not guardrails), updates to data handling (like supporting new symbol with proper config), adding a new integration read-only, etc. These can cause functional changes but are controllable and usually local to one aspect.
        
    *   **High risk:** Anything touching compliance logic, global system settings, or cross-cutting data schema. These can impact system compliance or stability in a way that might not be immediately obvious without deep analysis or can break trust in the tool.
        
    *   **Critical risk (needs exceptional care):** Introducing any form of automated order capability or disabling a safety – basically breaking the core premise. This is off-limits without a fundamental project direction change.
        

Engineers must approach changes with a “safety-first” mindset. If unsure about the impact, err on the side of caution: label it high-risk and get extra review or test coverage. The architecture favors safety over speed, and all team members should internalize that when making modifications.

*   **Rollback Strategy for High-Risk Changes:** Always have a quick way to undo a high-risk change:
    
    *   If the change is in code and not easily toggled, keep the previous version ready (e.g., don’t delete the old strategy logic immediately; comment it or toggle via flag so you can flip back if needed).
        
    *   For config changes, know the last good values (maybe commit history or have a backup). If raising a limit causes issues, be ready to lower it back promptly.
        
    *   Because we use Git and tagged releases, rolling back usually means checking out the last tag and redeploying. That should be practiced to ensure it’s smooth. The ticket logs and DB being forward-compatible (older code can work with newer data formats if those didn’t change drastically).
        
    *   If a deployment goes bad mid-day, one could even stop the tickets-cron to halt new signals (safe state: system paused) and then apply rollback after market hours if immediate rollback isn’t feasible in the moment. That at least prevents compounding issues (like multiple bad signals). This scenario should be communicated to operators as part of operations: “if something looks wrong with signals, we may pause the system as a precaution.”
        

In conclusion, changes to this system must be evaluated through the lens of **risk to safe operation and compliance**. The monorepo architecture, with its modular design and tests, provides tools to manage change, but responsibility lies with engineers to classify and handle changes appropriately. Always ask: _Could this change cause the system to output something that violates program rules or misleads the operator?_ If yes or unsure, treat it as high-risk and proceed with extreme caution.

Despite the comprehensive design, some areas of the system are not fully documented or have implicit contracts that a new contributor should be aware of:

*   **Documentation Gaps:**
    
    *   Some documentation pages have **TODO/TBD markers** indicating incomplete sections[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/TECH-SPEC.md#L2-L9). For example, _TECH-SPEC.md_ mentions “Data Contracts – Tickets JSONL schema (TBD fill from existing docs)”[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/TECH-SPEC.md#L16-L23). While much of the ticket format is described in README and code comments, there may not be a single source of truth doc for it aside from what’s embedded in other docs. New devs should rely on the code (e.g., type definitions in sdk or examples in docs) to understand these contracts. If something is unclear (like exact meanings of certain ticket meta fields), it might not be explicitly written; ask the team or refer to code/test cases.
        
    *   The **Glossary** and certain integration docs are auto-generated and include placeholders (e.g., “Provide step-by-step instructions” still TODO)[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/GLOSSARY.md#L16-L24). This means some operational procedures (like how to exactly link a Tradovate account or NinjaTrader setup) aren’t fully detailed. There’s an expectation that subject matter experts (or the risk officer) will fill those in. So, if you’re tasked with say deploying integration with NinjaTrader, expect to do some exploratory work or talk to whoever wrote that section. It’s not all spoon-fed by docs.
        
    *   There isn’t a central **architecture diagram** (aside from ASCII art/mermaid flows) for the system; one has to piece it together from text. This can be ambiguous for understanding how all services connect. For example, the interplay between realtime overlays (codex) and base services is not fully explained to newcomers – it’s in code/overrides but not in high-level docs beyond mentions. If implementing changes to realtime feed, you’d have to decipher those overlay YML files and scripts (lack of narrative explanation is a gap).
        
    *   **Docs vs Code mismatch:** Some configuration or behavior might have drifted from documentation. For instance, documentation might refer to an environment variable or port that changed. We saw Full Dashboard (compose): 8080 in docs vs actually using 5180 port in current config[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/TESTING.md#L154-L162). This discrepancy can confuse. Always trust the code and compose files over older docs. When you find such mismatches, update the docs (the docs have been given emphasis in onboarding, so keeping them accurate is important).
        
*   **Implicit Contracts & Assumptions:**
    
    *   It’s assumed that **operators follow a certain workflow**: e.g., always use the provided ticket info to enter trades and not deviate. The system doesn’t enforce that – it’s a human process. This is an implicit contract: the tool provides safe recommendations, but if the operator doesn’t follow (like not placing a stop), the protection is void. New developers might not realize how much the system relies on operator discipline. When extending the system, keep in mind we’re assisting a human, not replacing them. For example, an implicit assumption is one operator = one tool instance. Multi-operator or multi-portfolio usage isn’t explicitly designed for, though multiple accounts are. If a new feature would allow multiple simultaneous users on one instance, consider how that fits the assumption (most likely, one instance is managed by one team as a unit).
        
    *   **Single-Account vs Multi-Account**: The system supports multiple accounts (fanout) for tickets, but the assumption is that all accounts are homogeneous (all are Apex evaluation or funded accounts of similar rules) because guardrails like consistency and scaling rules are based on Apex’s program. If someone tried to use this system for accounts with different rules (say two funded accounts with different max drawdowns, or a non-Apex account), the current guardrail logic doesn’t support per-account customization (except via maybe separate config per account, which isn’t built). This is an implicit limitation – not clearly documented. A new dev might think to generalize the guardrails for different account types; that would be a significant undertaking. As is, the code expects one uniform set of rules applied to all trades/tickets (if multi-account, presumably all accounts are under the same program type). This should be clarified if needed: we may need separate guardrails config if in future multiple account types need support. Right now, treat it as a gap – system not multi-program aware.
        
    *   **Assumed DB state:** The code often assumes the database has been seeded with at least some historical data and is kept up to date. If someone were to start the system fresh midday without ingesting history, strategies that need prior data (like VWAP or ATR) might malfunction or produce no signals initially (ATR might be zero if no history). This is implicit; the quick-start instructs to seed data[GitHub](https://github.com/QuantumFluxAlgo/prism-apex-tool/blob/150c635e3113144fce347052a8903fbeeaedc977/README.md#L94-L102). A new developer or operator ignoring that might see nothing working and not immediately know why. This could be documented better (“Always run make seed on first run or when adding new symbols”).
        
    *   **Naming and Tagging:** They use certain naming conventions (like prefix @prism-apex/ for packages, and specific commit tag naming). It’s implicitly expected that new packages or tools follow the same pattern (e.g., if adding a new top-level app, name it under apps/ and maybe prefix app- in alias). Also, commit messages appear to follow conventional format (feat|fix|chore, maybe referencing a ticket e.g. ABC-123). This might be mandated (contributing guidelines likely mention it). Not following could mess up their changelog generation or CI triggers. So though not heavily enforced, it’s an implicit practice.
        
    *   **Performance constraints not explicit:** For example, how many symbols can it realistically handle? It’s not stated, but assumed the list is limited (there’s a default set in env). If someone new wanted to add 100 symbols to YAHOO\_SYMBOLS, the system might bog down or hit API limits. Not explicitly documented as a limit. Recognize such practical limits – if heavy expansion is planned, architecture might need review (like use websockets or batched queries).
        
*   **Areas needing human clarification or update:**
    
    *   **Tradovate Integration Usage:** It is not clear if the Tradovate REST client (clients-tradovate) is actively used in the current system or a placeholder. A developer might see it and assume data from Tradovate is flowing in, but it might not be configured (no tokens provided means it’s dormant). Confirm with project leads whether Tradovate integration is enabled and what data they expect from it (account balance, etc.). The strategy might not get new bars; does it keep last known values or skip signals? This is not thoroughly documented. It might be fine (just no new tickets), but as a dev, if you handle such an edge case (like holiday or API outage), you may need to discuss with the team what the desired behavior is (pause signals? notify operator?).
